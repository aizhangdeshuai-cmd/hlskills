# 项目知识库使用说明

`knowledge/` 下的 Markdown 随项目保存。其他人或新会话拿到同一版本的仓库后，可以用相同的术语检索到相同的原文。检索器随技能分发，使用 Python 3 标准库。已有 Markdown 可以直接查询，无需迁移、调用模型或手动刷新索引。

## 查找和核对

`HLKB` 指技能目录（内含 `kb.py`），`PROJECT` 指要查询的项目根目录。下面演示在项目根运行命令，把第一行的示例目录换成技能实际位置。

```bash
HLKB="/实际路径/hlskills/hlkb"
PROJECT="$PWD"
python3 "$HLKB/kb.py" --root "$PROJECT" search 'REFUND_TIMEOUT' --limit 1
```

从输出取项目相对路径和行号。如果命中 `knowledge/error-codes/README.md:27`，要核对相邻的处理条件，可执行：

```bash
python3 "$HLKB/kb.py" --root "$PROJECT" read knowledge/error-codes/README.md 27 --lines 8
```

优先用识别度高的关键词，如业务名“退款冲正”、配置名或接口路径。检索结合章节标题、命中行和紧邻的正文判断相关程度。表格逐行匹配，相关程度相当时优先显示声明为现行的条目。摘录保留章节或相邻正文以及状态，未标注的显示“状态未注明”。默认最多 3 条，输出上限 1,100 个字符。摘录不足时用 `read` 从命中行起读，单次上限 2,000 个字符。零命中时可从词表找别名再查。结论冲突时沿来源核对决定和版本，仍无法确认则写明争议。查历史规则时加入版本词，如 `v1 退款 超时`。日常检索跳过 `knowledge/doc/`。按验收编号核对当前版本时，用 [交接包查询](SKILL.md#找回知识)的 `--handoff` 范围选取产品索引指定的版本；历史包可显式指定完整目录。

每个项目的索引都可从 Markdown 重建。设置了 `XDG_CACHE_HOME` 时使用其下的 `hlkb/`，否则使用系统用户缓存。受限宿主写不了默认位置时，会尝试当前用户的私有临时目录，供后续查询复用。可用位置均无法写入时，命令会提示并在内存中检索。

## 接收常见改动路径

接收 hllegacy 的修改清单、分层规范和检查结果时，先用业务动作、规则名或代码符号查重。沿用现有 `knowledge/`，一个主题只维护一处正文，其他位置链接该节。

- **逐项修改清单**写在最贴近业务动作的现有条目，如状态机。清单后紧跟核对范围、排除理由、未核部分和实际验证结果。测试库已有用例时引用其编号与位置。
- **分层开发规范**写在对应模块或已有技术设计条目中。跨模块共用的规则只存一份，各动作链接该节。保留已批准约束、工具强制项及观察到的惯例各自的依据。
- **规范冲突**在受影响规则旁用独立小节记录。尚无处置决定时，以“冲突主题（待裁决）”作标题，保留双方来源与确认途径。裁决后原位更新处置、批准依据和生效范围。

动作没有合适主条目时，可复用已有的 `knowledge/tests/` 存放模块条目。现有目录都不适合时，直接使用 `knowledge/README.md` 的命名小节。首次建库也从这个文件开始。保存后按业务动作、代码符号、层名或规则名执行普通 `search` 并 `read` 回原文，核对改点、验证依据及冲突状态。

## 接收旧项目交付物

完整接手包含九个逻辑章节，可以分布于现有技术设计、接口、数据库、设计规范或质量条目。先按业务名和代码符号查找已有正文，把[对应类型标记和核验字段](../hllegacy/verification.md)加在原处。每类保留一个验收入口，其他已有模块明细可通过链接继续维护。找不到主条目时用 `knowledge/README.md` 的命名小节，首次建库也可只用这一份文件。给已有截图、报告和原始记录写引用。

归档后从目标项目运行全量或单项检查。新交接按[实测对照与证据移交](../hllegacy/verification.md#实测对照与证据移交)核验。任务速查链接到唯一修改清单，并给出首条复验命令。将可共享的采集记录随项目携带，多个证据根可用项目内相对目录绑定。另起一次普通 `search` 找回业务词、规则名或 `hllegacy:api` 类别标记，按行 `read` 核对适用版本与结论。交接列出实际文件和标题、机器结果、人工复核及未完成项。

## 同步触发表

下列路径均相对于项目根下的 `knowledge/`。新项目先在 `README.md` 标出已有类别和常用入口。沿用既有条目的路径、编号和标题，有新模块时再加条目或目录链接。只打开本次变更需要的模板。

| 变更 | 写入位置 | 内容与模板 |
|---|---|---|
| 产品包交付 | `prd.md` | 产品段步骤 12 归集 BL、AC、生效版本和对应包，标明待实现项 |
| 新术语或别名 | `glossary.md` | 标准名称、别名、定义与代码命名。[术语模板](templates/glossary.md) |
| 接口契约 | `api/{module}.md` | 路径、方法、权限、输入、输出与错误。[接口模板](templates/api.md) |
| DDL、索引或外键 | `db/{table}.md` | 核对迁移，关系有变时更新 `db/er-diagram.md`。[表模板](templates/db-table.md) · [ER 图模板](templates/er-diagram.md) |
| 重大架构决策 | `adr/{NNNN}-{slug}.md` | 上下文、选择与生效状态；四位编号连续，旧决定保留并关联替代决定。[ADR 模板](templates/adr.md) |
| 状态转换 | `state-machines/{entity}.md` | 事件、前置条件及可达状态。[状态机模板](templates/state-machine.md) |
| 枚举值 | `enums/{enum}.md` | 枚举值、定义、来源及写入方。[枚举模板](templates/enum.md) |
| 错误码 | `error-codes/README.md` | 使用精确错误码、触发条件和处理方式。[错误码模板](templates/error-code.md) |
| 依赖 | `dependencies/README.md` | 实际版本、用途及约束，核对项目依赖清单。[依赖模板](templates/dependency.md) |
| 环境变量 | `env-vars/README.md` | 名称、用途及环境差异，示例使用占位符。[环境变量模板](templates/env-var.md) |
| 验收用例、代码测试 | `tests/{module}.md` | 关联 AC、测试代码路径、执行证据及版本。[测试模板](templates/code-tests.md) |
| 已修复缺陷 | `pitfalls/{slug}.md` | hlbug 步骤 14 写触发条件、根因、修复及验证。[踩坑模板](templates/pitfall.md) |
| 版本复盘 | `retro/{包相对路径}.md` | 产品段步骤 12.5、开发段交付后步骤 15.5 续写同一包。历史包 `docs/v7` 与新包 `knowledge/doc/v7` 各有独立条目。[包身份与历史归属](../hlpm/path-conventions.md#022-包身份与复盘) |

新条目从上表对应模板复制到项目库，填写已经核实的事实。接口条目可用一次实际请求核对字段和错误响应；状态机条目可沿一次业务事件核对前置状态、动作和结果状态。

## 交付自检

1. 从本期契约、迁移、配置、测试及版本包的差异列出受影响的条目。开发段步骤 12.7 发布自检逐项对照上表。需要新建或更新宿主约束时按[项目约束文件规则](SKILL.md#项目约束文件)处理。
2. 在原文核对字段、状态、生效版本和证据。对替代项再用旧名称搜索一次，确认读者能沿指针找到新结论。索引命中只能定位，正确性要靠来源验证。
3. 交接提供本期实际更新的条目及依据。适用项缺失时先补齐。需要让其他设备或协作者取到这些记忆时，确保相关 Markdown 已按项目流程随代码提交和同步。

升级旧项目的宿主约束文件时，若仍有旧模板生成的“读 `knowledge/`”“读 `.hl/memory/`”全量读取步骤，只将该段更新为[现行模板](templates/claude-md.template.md)的“查找已有知识”。保留项目自行约定的必读材料。
