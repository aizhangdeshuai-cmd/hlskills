# hlchain — 全流程编排

> 属于 `hlskills` 技能系统。**编排器**(orchestrator)类型技能, 不包含新流程, 而是**依次加载其他 6 个子技能**完成端到端。

> ## ⚠️ 能力边界声明
>
> 本技能**没有真正的编排器 runtime**——不是 hook / 不是状态机 / 不是自动门禁。Agent 加载本 SKILL.md 后**按文档顺序自觉**依次调 `Skill hlpm` → `Skill hldev` → ...(漏一步不自动阻断;Agent 模型弱或 prompt 冲突时需手动打断重读)。**所有"阶段门禁"靠 Agent 自觉 + 用户手动打断**。
>
> 详见 `README.md` 「⚠️ 能力边界声明」。

---

## 编排的 6 个子技能

| 执行位置 | 调用 Skill | 交接物或条件 |
|---|---|---|
| 产品 | `Skill hlpm` | 进入开发前需完整交接包及验收依据。自定义链路若仅交 PRD 或原型，返回相应成果后结束。 |
| 开发 | `Skill hldev` | 在同一目录完成步骤 0 接收；交付候选 SHA、适用测试、审计与交付记录。 |
| 发布前补充验收 | `Skill hltest` | 当 UAT、兼容性或压测为放行条件时，在 hldev 步骤 11、合并与发布前执行，报告绑定候选 SHA。 |
| 发布 | `Skill hlrelease` | 远端标签、已通过必需 CI 的确切提交、发布记录与适用的不可变产物标识。 |
| 部署 | `Skill hldeploy` | 以已核对的发布记录部署指定环境，交付版本、健康检查和回滚信息。 |
| 任一阶段发现缺陷 | `Skill hlbug` | 修复后回原阶段，以新的候选重新取得所需证据。 |

---

## 模式 C (A+B 结合): Agent 自觉顺序 + 显式交接段

### A: Agent 自觉顺序
加载本 SKILL.md 后, Agent 按上述表格顺序逐阶段加载, 每完成一阶段核对对应产物、版本和验证结果，再进入下一阶段。

### B: 显式交接段
各阶段按交接段返回当前链路。由当前链路确认是否继续，沿用已选择的范围和版本。

---

## 用户调用示例

### 完整全链路

```
用户: Skill hlchain "为订单列表加导出 CSV 按钮"

Agent:
  1. 加载 hlpm （产品段，按需求执行适用步骤）
     输出: knowledge/doc/v1/ 下本次适用的交付物 (prd.md / test-cases.md / 设计稿 HTML 等)
  2. 询问用户: "产品段完成, 是否进入开发段?"
     用户: "继续"
  3. 加载 hldev (15 步开发段)
     输出: 候选提交、同提交的测试与审计；若有发布前 UAT，在此执行 hltest
  4. 询问用户: "开发段完成, 是否发布?"
     用户: "发布"
  5. 加载 hlrelease
     输出: 核验远端 v1.0.0、候选 SHA、CI 和实际发布结果
  6. 询问用户: "是否部署到生产?"
     用户: "先不, 我自己部署"
  7. (跳过 hldeploy) 链结束
```

### 跳过/替换/终止

用户可在任意阶段说:
- **"跳过 hlrelease"** → 跳过发布阶段
- **"在这里停"** → 终止编排, 不调下一个
- **"改用 hlbug"** → 当前阶段挂起, 调 hlbug 修, 修完回到原阶段

## Agent 加载本技能后的执行规范

### 第零步: 项目约束文件初始化

先沿用本项目已有约束。链路范围未定时先执行下节选范围。只交 PRD 或原型时，按所选范围调用 hlpm。含正式交接或后续工程阶段的链路按下列方式初始化项目约束：
- 检测项目根 AI 约束文件(Claude Code→`CLAUDE.md` / Codex→`AGENTS.md` / Cursor→`.cursor/rules/*.mdc`;多宿主使用本次选定的规则，记录实际路径)
- 不存在 → 按 `hlkb/templates/claude-md.template.md` 创建
- **创建时先去重全局约束文件**(Codex→`~/.codex/AGENTS.md`,Claude Code→`~/.claude/CLAUDE.md`),全局已有条目不写入项目级(v33,减少重复加载;详见 `hlkb` §项目约束文件)
- 已存在 → 校验是否含 `## 🚨 完成前自检` 段,缺则追加该段(不重写其他)
- 详见 `hlkb` §项目约束文件(注:被编排的子技能 hlpm/hldev 等其 step 0 也会做此检测,重复检测幂等,不冲突)

### 第一步: 确定链路范围

先采用用户已选的运行范围，未明确时确认 A 完整链路、B 核心四阶段、C 仅产品与开发或 D 自定义。若范围含部署，再确认目标环境。产品段的交付终点、启动问题和评审时机按 [hlpm 启动与选版](../hlpm/SKILL.md#启动与选版)确定，沿用已提供的信息。

### 第二步: 按用户回答展开链路

- 如果选 A: 执行全部适用阶段；hlbug 仅在发现缺陷时触发
- 如果选 B: 跑 hlpm → hldev → hlrelease → hldeploy, 补充测试按项目验收要求插入开发段；发现缺陷时调用 hlbug
- 如果选 C: 跑到 hldev 结束, 后面的让用户手动
- 如果选 D: 按用户指令展开。范围仅到 PRD 或原型时，将所选终点传入 hlpm。安排 hldev 接手时，将“完整交接”传入 hlpm；用户后来要求从轻量成果继续，先在原版本补齐完整包。

### 第三步: 每阶段完成后检查输出物

进入下一阶段前核验以下证据。证据缺失或必需检查失败时返回原阶段。

| 阶段 | 验证输出物 |
|------|----------|
| hlpm → hldev | 按[完整交接清单](../hlpm/handoff-package.md)核对适用产物与内容，传实际目录、确认过的验收计划、产品留存的计划与正文摘要、适用条件和页面清单。 |
| hldev 完成 | 用交接基线的必测 TC 核对实际候选 SHA、原始测试记录、审计及适用的发布前 UAT。场景或证据有缺口时回原阶段，丢弃候选时结束链路。 |
| hlrelease 完成 | 按 [发布流程](../hlrelease/SKILL.md) 核对远端标签、CI 与候选 SHA，确认适用的发布任务成功及预期产物已生成。 |
| hldeploy 完成 | 部署环境、已发布版本与实际运行版本相符，必需健康与观察结果已记录。 |

### 第四步: 每阶段完成后询问用户是否继续

已到本次指定终点时，返回实际产物、验证结果及待确认项并结束。以下为下一段已安排开发且产品完整交接检查通过时的示例。

```
hlpm 完成。输出物已生成于 knowledge/doc/v1/。
下一步: 加载 Skill hldev 开始开发?

[选项]
- A. 继续 (加载 hldev)
- B. 暂停 (我先看看产品段产出, 之后再继续)
- C. 跳过 hldev, 由 hlrelease 核对已有候选和必需测试后发布（只改文档时亦适用）
```

### 第五步: retro 模式回顾(周期性, v32,技能自我进化提案)

每完成 3 个版本(或用户主动要求)时执行:
1. 从项目根运行 `python3 "$HLPM_DIR/version.py" retro .`。按[复盘约定](../hlpm/path-conventions.md#022-包身份与复盘)匹配实际包路径，按完成日期取最近三个已完成的不同包，并读取相应记录与 `knowledge/pitfalls/`。同包的两阶段、修订及旧文件只计一次。报告少于三期或历史记录归属不明时列出实际样本和待核项。
2. 找"同类信号出现 ≥3 次"的模式(如同一类评审驳回反复出现 = 对应技能的规则有缺口; hldev 反复拒收同一类问题 = hlpm 该改)
3. 输出**技能修改提案清单**(改哪个技能哪个步骤、改什么、依据哪几期 retro 的哪些信号)
4. **只提案,不动技能文件** — 提案交用户审,确认后才改技能仓库并 bump 版本注记

---

## 强制约束

1. **不修改任何子技能的核心流程**: hlpm / hldev / hlrelease / hldeploy / hltest / hlbug 的步骤不变, 仅在每个 SKILL.md 末尾加"## 交接段"段
2. **不做覆盖: hlchain 不替代上述 6 个技能, 只是顺序加载它们**
3. **所有"自动门禁"靠 Agent 自觉**: Agent 不会因 hlchain 缺失某阶段而拒绝继续
4. **失败处理**: 任一阶段失败 (如 hlpm 被拒收), hlchain 应建议回到前一阶段或终止
