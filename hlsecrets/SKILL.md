# 代码敏感信息扫描

独立调用或配合 `hlreview` 时由 [security-reviewer](../agents/security-reviewer.md) 只读检查。依据《代码敏感信息扫描》导出规则 v1.0，适用于所有语言（`all`），类型为 `security`。报告反映本次静态检查所见；凭证是否有效、权限大小及是否已被使用，不能从字面量推定。

## 开发时使用

`hldev` 的实现者写到认证、连接串或配置时，沿用项目已有的凭证注入方式。必需凭证缺失时走项目约定的错误路径，避免在源码或配置里留下硬编码回退值。测试使用虚构值，日志和错误仅记录必要的字段名及状态。

提交或交评前按下表启用的规则检查本次交付的源码、配置、注释和新增文件。优先使用项目已有的脱敏扫描；没有扫描器时逐文件核对，记录实际覆盖范围。工具输出和交接只保留位置、类型和遮蔽后的证据。发现确证凭证时先移除并复查拟提交版本；若已进入历史，脱敏告知维护者处理轮换。

## 规则

| 编号 | 名称 | 分类 | 严重度 | 默认状态 |
|---|---|---|---|---|
| HL-001 | 硬编码扫描 | security | high | 启用 |
| HL-002 | 代码专项扫描 | security | high | 停用 |

严重度权重沿用源配置：critical = 10，high = 5，medium = 2，low = 1。两条规则的结构化级别均为 high。默认只执行 HL-001；HL-002 不产生发现、不计分。只有用户明确要求启用 HL-002 时，才按其补充清单复核。

## 审查流程

1. **界定范围。** 用户指定了 diff、文件、目录或代码片段时按该范围检查；要求检查项目时检查项目内源码、配置（含隐藏配置，如 `.env`）和注释。区分工作树与提交历史，记录实际检查范围、排除项、未读文件和原因。
2. **按 HL-001 查找候选。** 检查赋值、配置值、授权请求头、注释和连接串。字段线索包括 `password`、`pwd`、`secret`、`token`、`apikey`、`access_key`、`secret_key`、`private_key`、`auth`、`bearer` 及其语言命名变体。复核直接写入的明文或高熵值、AWS（AKIA）、阿里云（LTAI）、腾讯云（SecretId/SecretKey）的凭据组合、JWT/Bearer 字面量、RSA/ECDSA/SSH 私钥材料，以及带明文密码的数据库 URI。搜索工具只输出路径、行号或已遮蔽的结果。
3. **复核上下文。** 排除测试或 mock 用例、明确的示例或占位值（如 `xxx`、`your-key-here`）、只提及字段名的声明、单纯从环境变量读取的值（如 `process.env`、`os.Getenv`、`System.getenv`）。源规则也将 `123456` 列为占位示例：示例文档中可排除，实际认证配置中若被当作密码使用则报告。环境变量读取附带硬编码回退值时，单独核对回退值。仅凭高熵、公开标识符或私钥头部示例不足以确认泄露。证据不足的候选列为待核实，和已确认的硬编码分开。
4. **去重并报告。** 以文件、行号和同一赋值或凭证块定位发现；多行私钥算一处，同一处触发多个特征或两条规则时只报告一次，列出实际启用且命中的规则编号。不同位置分别列出，方便维护者逐处修复。静态检查不向服务发送凭证进行验证。

### HL-002 补充清单（仅显式启用）

- 密码与令牌：检查 `passwd`、`db_password`、`database_password`、`admin_password`、`root_password` 等，以及 API、Access、Secret、OAuth、Bearer 和 JWT 的具体值。
- 云和加密材料：覆盖 AWS Access Key ID / Secret Access Key、阿里云 AccessKeyId / AccessKeySecret、腾讯云 SecretId / SecretKey、Azure ClientSecret、Google Cloud API Key、RSA/SSH/PEM 私钥及 AES/DES 密钥。
- 数据库与配置：检查 MySQL、PostgreSQL、Redis、MongoDB、Oracle 的连接配置，尤其是 `.env`、`application.properties`、`application.yml`、`config.json` 和其他 YAML 配置。
- 同样排除测试数据、示例和没有具体值的字段。报告“敏感信息硬编码泄露”、泄露类型、影响及修复建议。采用规则元数据的 high，保留上下文对实际影响的说明。

## 输出与完成检查

先写范围、启用的规则和覆盖缺口，再逐项报告：

| 规则 | 问题名称 | 等级 | 文件:行号 | 泄露类型 | 脱敏证据与潜在影响 | 修复建议 |
|---|---|---|---|---|---|---|
| HL-001 | 敏感信息硬编码泄露 | high | 示例：config/db.yml:12 | 数据库密码 | 连接配置直接赋值为字面量；获得配置的人可能访问对应数据库 | 从密钥管理服务注入，并由维护者轮换已暴露的密码 |

证据只写字段名和赋值用途。值统一写作 `[已遮蔽]`；报告、命令输出和日志都不复制原值、可还原的片段或整行连接串。

修复建议可包含从环境变量、配置中心或 Secret Manager 加载凭证。若已提交到版本库，建议维护者先撤销或轮换，再协调清理历史，并考虑在提交和 CI 中使用 Gitleaks、TruffleHog 或 git-secrets。此次审查的交付物是报告；轮换或改写历史需要单独授权。

- [ ] 每条发现都有实际位置、脱敏证据、泄露类型、等级和针对该处的修复建议。
- [ ] 停用规则未混入结果；同一处发现只统计一次，待核实项单列。
- [ ] 零发现时说明“在已检查范围内未发现硬编码凭证”；文件不可读或输入截断时明确列出遗漏范围。

两条规则的分类依据见 [CWE-798](https://cwe.mitre.org/data/definitions/798.html)。
