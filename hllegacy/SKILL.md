# 旧项目首次分析流程

> 本技能的 G1–G4 关卡是文档纪律，靠执行者核对证据和用户签批；没有 runtime 强制。

完整接手按下表顺序执行。单问“改哪里、怎么验”直接查 [逐项修改清单](change-review.md#逐项修改清单)，提炼某层规范查 [分层约束](change-review.md#从源码提炼分层规范)，核验某类交付查 [九项标准](deliverables.md)。只分析时在答复中给结果。建档时由 hlkb 写入项目知识库，业务代码只读。

## 分析流程

| 阶段 | 实际工作与交付 | 进入下一阶段的条件 |
|---|---|---|
| 0 确定边界 | 列出工作区、归档仓、只读仓、各自分支或快照、提交、影响结论的本地改动、统计时间窗及归档位置。先在 hlkb 按业务动作、符号查既有正文。 | 归档仓与范围可确定。有歧义时列实际候选请用户选择。无源码时说明可核范围。 |
| 1 源码事实 | 按[事实层提纲](change-review.md#事实层提纲)盘点模块、运行入口、依赖、数据流、所有业务入口及实际页面。选本次任务或有历史依据的改动追到调用、存储和消费端。采集九类交付所需的执行证据。 | **G1** 数量、身份与独立清单逐项一致。抽查三个源码符号、实际构建或启动方式，记录分支、提交、日期、命令。 |
| 2 项目约束与贯穿示例 | 从事实提炼各层的强制写法、禁止项、存量例外及替代方案，每条链接源码或项目决定。使用一个代表性任务贯穿所有相关层。 | **G2** 逐项对照分层必查表与示例，登记正例、冲突、实际运行结果。适用层的缺项须补齐。[分层与示例验收](change-review.md#从源码提炼分层规范) |
| 2.5 外部集成 | 按真实技术载体分别归集入站和出站、客户端清单、失败处理与变更步骤，引用现有分层规则。没有此类集成时给出依赖、注册、调用三者的核对范围。 | **G2.5** 逐节核对来源映射、两处数量、冲突及确认路径，写明权威条目、日期与提交。[集成验收](change-review.md#外部集成视图) |
| 3 接手决策 | 先保存各仓的提交画像，再用当前源码核实高频改动。首页用一屏速查回答改哪里、如何复用、怎么验，链接到每类改动唯一的施工单。 | **G3** 用三件真实历史需求让独立读者只读手册判定落点，再揭晓实际改动核对。报告匹配、误报与漏项。[手册及验收](change-review.md#接手决策手册) |
| 4 归档与授权 | 由 hlkb 更新既有章节。从普通检索入口用业务词找回改点、用符号找回规则，核对证据和适用版本。分别交付九类自动项、人工复核和阶段门禁结果。 | **G4** 需求负责人逐条确认拟用作开发红线的规则后，方可按该手册接实施需求。待签批时仍可交付事实和核验记录。签批人、时间、范围必须有记录。 |

事实是规则和手册的依据。对事实的修订从源码、配置或实测开始，修正原条目再更新引用。新旧写法并存时在影响模块分别记录新增规则、存量处理及裁决依据。只有已确认需一起迁移的范围才进入改动清单。

## 九类交付与保存位置

[九类交付标准](deliverables.md)逐项给出主表、硬性要求、禁止内容、验证与退回条件。新交付按[核验协议](verification.md)使用 `--require-observations` 核对数据库、API、UI 的实测断言。专项用 `--only` 选择类别。旧稿复查时区分结构通过、已有运行证据和仍待补证的结论。

| 交付物 | 核验参数 | 交付物 | 核验参数 | 交付物 | 核验参数 |
|---|---|---|---|---|---|
| 技术栈 | `--only stack` | 模块架构 | `--only modules` | 逻辑架构图 | `--only architecture` |
| 数据库与 ER | `--only database` | API 与入口 | `--only api` | 前端规范 | `--only ui` |
| 代码质量 | `--only quality` | 安全基线 | `--only security` | 技术债 | `--only debt` |

每个阶段结束，给出更新的绝对路径、章节与行数、可核查的数量、失败项和未决冲突。全套产物复用项目既有 `knowledge/`，事实、规则、集成视图和决策速查是其中的章节职能。每个主题保留一个正文，缺合适主题时续写 `knowledge/README.md`，首页和各视图只链接明细。证据与复验命令一同交接，具体格式见[核验协议](verification.md)。[hlkb 归档与检索约定](../hlkb/README.md#接收旧项目交付物)

## 角色与下游

按[角色加载方式](../SKILL.md#agent-使用方式)读取本阶段需要的角色。架构与代码使用 `architect`，实际前端由 `architect` 与 `designer` 核对源码和渲染，安全使用 `security-reviewer`。视频交互取证按需使用 [hlmedia](../hlmedia/SKILL.md)。只有任务还要求初始化宿主时才按 [hlkb](../hlkb/SKILL.md) 设置宿主规则文件及知识指针。

开发与测试接收同一份改动清单、可运行示例及失败判据。已有行为回归和新需求验收分别标出。重构、需求分析或缺陷修复时，分别把条目位置、适用版本和待裁决项交给 hlrefactor、hlpm 或 hlbug。
