# 从源码梳理改动与开发规范

完整接手按下列提纲组织现有知识章节，专项直接读对应章节。统计写清仓库、分支、提交、日期与命令。每节先写结论，再给源码位置或脱敏实测，结尾列可逐项勾选的检查。

## 事实层提纲

| 任务 | 章节顺序与验收 |
|---|---|
| P1 项目全景 | 整体架构与目录树 → 模块职责及调用方 → 业务域与完整入口表 → 关键类、函数和实体 → 依赖与外部系统 → 构建、启动、测试、配置 → 数据访问 → 本仓编码约定与特有机制。表标题写实测个数。一项事实只维护一次，其余章节链接。数据访问覆盖数据源与切换、ORM 与分页、映射文件、事务、分表、命名及公共字段，以仓库实际机制举例。 |
| P4 前端 | 多端先用同一张表横向对照框架、UI 库、状态管理、路由、图表、构建、安全、路由生成、用户及能力，再写各端职责，最后按业务域对齐页面到真实后端入口。单端写本端目录职责、分层与对接关系。页面目录与实际注册数分别核对，交互与截图按[前端交付标准](deliverables.md#6-前端设计规范文档)。 |
| P5 业务流程 | 有清晰业务流程时，依次写流程和状态总览、模块、实体、各入口操作、外部集成、横切机制与枚举。每个入口写路由或事件、业务位置与上下游、真实方法与操作表、关键字段或规则。状态列“值、含义、触发动作”，保留已废弃入口与混用方法。与运行入口清单双向对账。 |

G1 从独立的构建描述、注册表、目录或运行输出反查身份与数量，回到源码检索三个抽样符号。小仓不足三个时报告实际分母。启动方式未得到运行证据时写清已查配置和未运行原因。业务域按解决的问题命名。

## 逐项修改清单

P3 优先处理用户点名的业务动作。声称“最高频”要从固定时间窗的提交逐项归类，给出命中次数、分母和筛选方式。选择一个代表实例沿业务入口、调用、数据读写和消费端展开，按下列顺序编写。

1. **总览**。按类别列文件和改点数，分别汇总必改文件数、每个独立改点数、条件改点及仅验证项。同一函数里的两个行为变更分别计数。
2. **逐项施工单**。表头如下。每行有可定位的符号、修改方式或能直接复用的最小片段、遗漏的后果、预期行为。多入口、分表或生成物要指到各自权威定义与生成命令。

   | 类型 | 文件、符号和具体位置 | 改什么或检查什么 | 漏掉会怎样 | 怎么验证 |
   |---|---|---|---|---|
   | 必改、条件改或仅验证 | 仓库相对路径、函数或配置键、行号 | 实际操作，条件项注明触发条件 | 用户可见错误或数据影响 | 输入、操作、断言 |

3. **快速操作**。用同一个实例编号串起前置数据、步骤、首条复验命令、可观察的成功与失败结果。区分本版本的实测、候选方案及实现后的验收。
4. **类型对照**。列本任务容易写错的对应关系，例如表单字段原名、服务端读取键与是否多值，或数据类型、程序类型和文件格式。
5. **全局反查**。从注册表、配置绑定、消费者或序列化器独立反向定位，用别名和关键符号再查。以“路径、符号、改点”比较两份清单，解释命中但无须改动的项及未读到的范围。最后一项检查须能发现遗漏。

## 从源码提炼分层规范

**S1 单层规范。** 从入口、事务与数据、外部适配等实际职责划层。每层按结构与入口、方法参数、返回和错误、层内特有机制、禁止事项与替代写法、覆盖自检排列，正文最多 200 行。规则行记录适用场景、必须或禁止的写法、项目内正例、判定方法以及例外。使用本模块已生效的框架或组件，写出绕开既有边界、在错误模块定义接口的实际后果和项目内替代路径。根据层内实际代码核对原模板的五条以上禁令及替代框架边界，缺足够依据时列明缺项，不补造团队禁令。

**S1-L 分层必查。** 存在该层时，按下表编号逐项记录“命中及来源、经核实采用的替代机制、未核及原因”。读实现，也读配置、拦截器和注册入口。一整层经依赖和调用方反查确实不存在时，在适用范围说明。存在的层须逐项给出依据。

| 编号 | 数据访问 | 编号 | 远程调用 |
|---|---|---|---|
| D1 | 连接池、连接生命周期与配置类 | F1 | 客户端、数据对象与降级定义所在仓及模块 |
| D2 | 各数据源、用途、启用开关、动态切换 | F2 | 接口和降级命名、新旧例外 |
| D3 | 配置键的真实层级与生效来源 | F3 | 客户端注册、服务名、地址键、配置、降级绑定 |
| D4 | 慢查询阈值、监控、防护与多语句开关 | F4 | 服务名常量、地址配置与新增改点 |
| D5 | ORM、通用映射、扫描、方言及空值策略 | F5 | 方法、参数、校验、头与动态地址 |
| D6 | 分页、参数/默认值、越界及起始页 | F6 | 响应类型、失败码、调用方分页边界 |
| D7 | 实体位置、主键生成、表映射与序列化 | F7 | 降级工厂、异常传播、错误与假成功判据 |
| D8 | 公共审计字段、必填及例外 | F8 | 熔断/隔离配置及开关 |
| D9 | 自定义查询接口、SQL/映射文件归属和绑定 | F9 | 透传头名称、来源及手工参数边界 |
| D10 | 声明式、编程式事务和各自适用位置 | F10 | 启用方式、注册与实际扫描范围 |
| D11 | 分表键、分区与访问封装 | F11 | 客户端、用途、服务名及实际数量 |
| D12 | 命名、外键、关联字段、多值存储与去重 | F12 | 传输对象按系统的目录与命名 |

**P2 贯穿示例。** 使用同一个贴近本仓的需求，按流程、数据、接口、逐层实现、特殊场景、质量要求、验收清单、文件速查排列。源码已有做法作正例。候选新增符号先查重，示例明确标注，并给出可在隔离样例运行的完整调用或可编译片段、位置、命令、输入与预期。在只读分析中用临时副本验证示例，项目知识只保存必要片段或链接。数据设计记录命名与前缀、布尔映射、公共字段、主外键及关联/多值约定。每个实际特殊场景说明何时复用、漏掉的后果。分层规范形成后交叉检查示例，列出不一致及解决状态。

**G2。** 规则须区分已批准要求、工具或测试强制、观察到的惯例。抽一条可执行规则回读三个不同正例并核查涉及的新代码。记录实查数量，实例不足或没有本次改动时明确边界。对适用层的每个 D/F 编号标明核对结果，未核项数应为零。未运行的示例、冲突或未满足的门槛单列，不判该项通过。

普通分层规范用 `standard` 核对长度、禁止事项和覆盖自检。数据访问或远程调用的“覆盖自检”可用三列表格，依次填编号、✅/❌、源码位置（如 `src/orders.py:42`）。也支持原版紧凑写法，如 `D1 ✅ D2 ✅`。此时在前文对应小节标题标出编号或范围，如“连接与配置（D1–D4）”，正文给源码路径或可检索的符号。机器核对数量、编号、未核标记及锚点文本。打开源码判断正例和替代机制是否成立，仍需人工复核。

```sh
python3 "$HLLEGACY/verify_handbook.py" --root "$PROJECT" data 'knowledge/README.md#数据访问规范'
python3 "$HLLEGACY/verify_handbook.py" --root "$PROJECT" remote 'knowledge/README.md#远程调用规范'
```

## 外部集成视图

P6 先读取该载体的分层规范、依赖/系统清单、贯穿示例、业务入站入口和对应决策配方。为每个实际载体（如远程调用、消息、文件存储、单点登录）在现有正文中分别设节。文首声明权威分层条目、采集日期/提交、所读范围和来源性质。依次记录总览及定位、出站契约、降级与失败、请求头/链路、调用方、入站入口、客户端或连接数、数据对象、启用与扫描、增改步骤、禁止事项、自检及来源映射。只列真实存在的方向和机制，缺失项给可核实的原因。原模板要求至少八条禁令，其中至少两条覆盖绕开载体自建通道。逐条链接已有规则及后果，核对来源。如真实项目的可证规则不足，记录原标准未达和实际数量，聚合视图禁止自行增设规则。

**G2.5。** 将对应分层规范的每个二级主题映射到本视图的位置，总览与明细客户端数相同，入站入口与注册项身份相同。抽查三个客户端到来源，少于三个报告实际数。差异给裁决或明确确认路径。首次生成遇到尚无决策配方时，先从事实和约束建视图，完成下阶段手册后回查双向引用。

在现有聚合视图的“来源映射”小节中按来源各写一张两列表。第一列表头写 `knowledge/规范文件.md#规范章节 二级标题`，第二列写“本篇位置”。首列逐行填来源规范每个直接子标题，次列填视图的完整子标题，多处以中文分号分隔。整篇规范可省去 `#章节`。已有编号视图也可写“一、十一”。工具核对遗漏、重复和实际落点。各方数量、证据含义与冲突裁决另行复核。

```sh
python3 "$HLLEGACY/verify_handbook.py" --root "$PROJECT" integration 'knowledge/README.md#文件交换' --source 'knowledge/README.md#存储规范' --source 'knowledge/api.md#附件规范'
```

## 完整性和规范冲突检查

对照源码、测试、配置与已批准决定。两种写法并存时逐项给出双方路径与版本、在同一统计范围内各占 M/N、受影响的新增与存量行为。判定当前行为时，优先看需求所在模块最近实际执行的代码和测试，其次查分层规范，再查事实层示例。判定新改动时，记录适用的已批准要求和例外，给出“新增采用什么、存量怎么处理”。已批准要求与实现偏离时保留差异并请有权角色裁决，禁止借“最近”或“多数”替项目批准规则或发起存量迁移。

## 接手决策手册

D1 只在现有入口维护一份。开头用 8–10 行问答作 **30 秒速查**，读者应能找到真实需求入口、首读文件和符号、可复用能力、必改和禁改边界、首条可复制验证命令以及预期结果。命令注明工作目录、可获得的样例与前置依赖。正文引用同一份修改清单和证据。

1. **按仓统计。** 完整接手默认近一年，每个相关仓以选定分支及提交统计总提交、非合并提交、文件变更次数、均值/中位数、单文件及至少十文件提交的比例、主要作者、前八目录、各实际层和前十热点文件。用下方命令生成统计，随条目保存原表、命令和重命名口径。实际代码层与目录的对应关系由项目入口和构建配置核实。无 Git、浅克隆或缺历史时标明范围，不能宣称已经验证了高频改动。

   ```sh
   python3 "$HLLEGACY/git_profile.py" --root "$REPO" --ref "$REF" --since "$SINCE" --until "$UNTIL"
   ```

   需要按层汇总时，按实际仓库布局追加 `--layer 名称=仓内目录或文件`。可为同一层指定多个目录，重叠路径按最具体的条目归类；未匹配项会单列。

2. **形成决策。** 每张表写一条与当前源码核对过的解读。手册按速查、系统全景、提交画像、拟定/生效红线、分端或分层配方、跨层步骤、历史踩坑、Git 约定、知识索引、一句话原则收束，最长 800 行。配方有定位顺序、编号步骤、复用项和验收。历史坑写“现象、后果、正确做法与提交”，举证后按原模板覆盖十项自检和十项常见坑，证据不足记未达项。规范冲突附具体比例与裁决顺序。
3. **G3 可用性验收。** 选三项真实历史需求，只给独立读者需求描述与手册，请其判断落点、要改和不应改的文件、验证方法。随后与对应提交的实际变更及当时版本对账。原模板以每项能定位 3–8 个文件衡量常见改动。真实改动更小或更大时，按实际清单核对并说明差异。缺样本、未隔离或作者自行回看时如实记录，不计作独立验收。
4. **G4 人审。** 对每条拟生效红线记录编号、依据、适用范围、负责人决定及日期。待审、退回、已确认逐项区分。负责人全部确认后，手册方可作为该范围的实施约束。已核事实、旧行为回归和未决问题随时可供查阅。

选取现有手册的精确标题运行结构核验。独立成篇时省去 `#标题`。仅运行任务适用的一条命令，将示例文件和标题换成实际位置。退出码 0 表示结构项通过，1 表示内容未达标，2 表示路径或章节无法读取。承担 G3 盲验和 G4 审批的角色分别记录自己的结论。

```sh
python3 "$HLLEGACY/verify_handbook.py" --root "$PROJECT" decision 'knowledge/README.md#接手决策手册'
```
