# 九类交付的机器核验与人工复核

hlkb 先把正文写入项目现有 `knowledge/` 条目。九项可共用一份 Markdown，也可分布在已有文件中。为已有知识补上对应小节和字段，保留原有说明；其他模块已有明细时链接原件。自动检查和普通知识检索使用相同的文档范围，跳过隐藏目录、符号链接和 `knowledge/doc/` 版本快照。

## 写一个可核验的章节

每类使用一个具名 Markdown 标题，以 `<!-- hllegacy:类型 -->` 结尾。公共字段各占一行。[九类规范](deliverables.md)列出每类主表的必需列、编写和复核要求。主表可增加列，标识在该类中唯一。下面的 API 示例展示字段用法，实际路径、日期、版本和结果须换成项目证据。

```markdown
## 订单 API 端点清单 <!-- hllegacy:api -->

范围：订单服务，部署到测试环境的 HTTP v1
版本：2026-11-24，main 分支提交 3b0e981，工作区干净
状态：完成
反查依据：spec/orders.json:8
反查清单：@openapi-json:spec/orders.json
实测对照：evidence/orders-http.json
核验：从注册入口核对 GET /v1/orders，回读鉴权中间件，运行订单契约测试 2 项通过。

| 标识 | 调用方 | 输入 | 输出 | 权限 | 证据 |
|---|---|---|---|---|---|
| GET /v1/orders | 商家订单页 | cursor（分页游标） | 200 application/json，返回本账户订单列表 | 商家登录、账户隔离 | app/routes.py:18；tests/test_orders.py:32 |
```

- **范围、版本**说明本次覆盖哪些仓库、环境和模块，以及结论对应的日期、分支、提交和相关工作区修改。无 Git 时给出能复核的源码快照。多仓分别记录版本。
- **证据**使用从项目根起算的 `相对路径:行号`，多个位置用中文分号分隔。抽查有名称的源码实例时用 `相对路径:行号#符号`，如 `app/routes.py:18#list_orders`，工具会核对该行包含该标识。指标、配置等也可以直接引用脱敏记录的非空文本行。外仓证据使用下文显式传入的源目录。同一知识文件中已有的原始规范可以引用，避免以本次报告循环自证。
- **反查依据与清单**记录第二种取证途径及其候选集合。较短时写 `反查清单：GET /orders；POST /orders`；仓库已有逐行一键的独立清单可用 `@相对路径` 直接读取。API 支持 `@openapi-json:相对路径`，从 Swagger 2.0 或 OpenAPI 3.0/3.1 的 JSON `paths` 解析方法、静态挂载前缀和本地路径引用。动态前缀、外部引用或项目的其他协议可用部署后的路由列表反查。人工录入候选时保留提取来源和复查方式。
- **图、截图**直接放在该节或引用原资源。架构图使用有方向的 Mermaid 连线或时序消息，主表起点、终点填图中的稳定节点 ID。ER 图用 `erDiagram`，主表的实体标识对应图中的实体。UI 主表的截图列填项目内实际 PNG、JPEG、GIF 或 WebP 的相对路径，记录对应的状态、版本和视口。
- **状态与核验**分别记录交付状态、本次执行的核验动作及实际结果。证据未取得或适用范围未查齐时写 `未完成` 并说明下一步。只有数据库、API、UI 确认不适用时可写 `不适用`；技术债经核对为零时可写 `无发现`。这两种情况保留范围、版本、反查依据、核验，另写 `理由：`。已有实物或记录与豁免矛盾时需重新核查。

## 运行和判定

`HLLEGACY` 为本技能所在目录，`PROJECT` 为保存知识库的项目根。使用 Python 3 运行，校验器只读。只运行当前任务对应的一条命令。

```bash
# 新交接，核验九类及实际取得的业务样本
python3 "$HLLEGACY/verify-deliverables.py" --root "$PROJECT" --require-observations
# 本次只交接 API 与模块
python3 "$HLLEGACY/verify-deliverables.py" --root "$PROJECT" --only api --only modules --require-observations
# 多仓项目。下游代码可用 client//src/orders.ts:12 引用，报告仍归档在 PROJECT
python3 "$HLLEGACY/verify-deliverables.py" --root "$PROJECT" --source client="$CLIENT_REPO" --only api --require-observations
```

退出码 `0` 表示所选类型的自动项通过，`1` 表示交付不合格或未完成，`2` 表示参数或知识库无法读取。检查覆盖类型缺失或重复、占位字段、逐项证据、候选标识差集、图表对照、截图路径与文件签名、技术债等级，以及已知高风险凭据形态。诊断按类型和位置定位。修正原条目后用同样范围重跑。

最后由执行者按各项禁令复核实际来源。如实记录抽样结果、受影响范围、原始截图与实际界面的一致性、冲突双方和剩余问题。脚本不会执行报告中写下的命令；测试结果须从实际运行或可信报告取得。风险基线发现问题时可以完成如实记录的报告，有待决的强制规则要保留裁决状态。完整交付需要九类逐项有结论、自动核验通过、人工复核满足各项条件，并能用 hlkb 的普通检索回读到证据。

## 实测对照与证据移交

新交接的 API、数据库和 UI 正文章节各写一行 `实测对照：evidence/capture.json`，可引用同一文件或各自已有采集记录。路径从项目根起算，也支持已绑定的 `名称//路径`。由请求探针、数据库元数据、浏览器或可信测试报告导出以下 JSON。记录采集范围、命令、应用版本及数据来源，保留可复跑的原件。下面演示字段形状，示例中的截图摘要须由采集到的文件计算。

```json
{
  "api": [
    {"id":"POST /items/export/","fields":{"columns":2,"export_format":1},"status":200,
     "content_type":"text/csv","attachment":"items-export.csv"},
    {"id":"POST /items/content/","fields":{"pk":2},"status":302,
     "content_type":"text/html","effects":{"rows_deleted":2}}
  ],
  "database": [{"parent":"categories","child":"items","nullable":false,"unique":false}],
  "ui": [{"id":"export","url":"/items/export/","action":"打开导出表单","sha256":"<原始 PNG 的 64 位十六进制摘要>"}]
}
```

| 类别 | 如何采集、正文如何写 | 校验结果的适用范围 |
|---|---|---|
| API | 用运行注册的“方法 路由模式”作 id。保留实际发出的字段原名及其提交次数。多值例在输入列写 `columns（可重复）`。输出列列出样例的状态码与 MIME，如 `200 text/csv`。无 Content-Type 时采集值写 `null`、正文写 `204 无 Content-Type`。导出样例应记录实际附件名，写操作应记录可观察结果，如 `rows_deleted=2`。用项目样库断言内容或最终状态。 | 每笔核对请求、响应及提供的效果，列出实测笔数与覆盖身份数。按本次任务覆盖所有涉及入口、关键成功和失败分支。未采样入口、未执行的协议及正文的其他事实另行复核。采集写操作时使用可回收样例。 |
| 数据库 | 从当前模式取得 FK 两端、可空性及完整外键列组的唯一性。多条关系同端点时用 `label` 区分并匹配图上的关系名。多列键按实际索引、空值与方言语义核对。物理外键确为零，写 `"database":[]` 和 `"database_basis":"evidence/schema.json"`，指向独立原件。 | 按外键方向与基数核对图，区分物理外键与逻辑关联。将原始外键清单、明细数及逻辑关系另行对账。其他唯一约束、业务要求或触发器带来的基数不能仅凭单个字段推定。 |
| UI | 以同次浏览器操作得到的 URL、动作及截图摘要登记状态。主表除已有六列，再加 `实测路径`、`实测动作` 两列，值与采集记录一致。一状态一条。截图需要遮挡私人信息时先在采集阶段完成遮挡，再计算摘要。 | 自动绑定状态、路径、动作、图片。交付者另查操作后的反馈、图中关键控件及视觉差异。 |

同一接口有多种结果时，可将主表的输入、输出两格均填 `见实测场景`，在同章用 `| 标识 | 场景 | 输入 | 输出 |` 分行写契约。采集项的 `case` 精确对应场景名，可选 `"values":{"format":"csv"}` 对应输入 `format=csv`，只记录公开枚举。负例可写 `columns[]（实发2次）` 描述实际发包，并用该场景的输出记录拒绝或无效果的结果。

API 正文可折叠框架自动生成的 HEAD / OPTIONS。在 API 章节写 `框架方法：@evidence/implicit-http.txt`，引用从实际注册导出、逐行一个标识的清单。`反查清单` 仍使用所有方法的完整身份。对应业务路由留在正文，自动 HEAD 须有对应 GET。手写方法或具有自定义业务行为的方法保留完整行。分别报告显式路由数、框架方法数、CLI 数和实测样本数。

优先复用项目中已有原始证据的位置。若交付中使用多个别名，可在 **现有 knowledge/** 放置可选文件 `hllegacy-sources.json`，例如 `{"common":"evidence/common","own":"evidence/legacy"}`。校验器自动读取，两条路径均相对项目根，支持搬移或重新检出项目。外部独立仓由接收方用 `--source 名称=实际目录` 显式指定，也可覆盖已有别名。归档时用干净目录重跑同一条命令，并用 hlkb 检索回读业务词。缺少外部材料时标明来源、未核范围和补齐方式。

历史条目可以直接运行原命令。已绑定的实测记录会自动核对，未绑定的适用章节会显示“仅结构核验”。新增完整交接使用 `--require-observations`。九类检查、[G2.5 来源映射](change-review.md#外部集成视图)、[分层规范及决策手册结构](change-review.md#接手决策手册)、独立读者试用及负责人签批分别登记结果。
