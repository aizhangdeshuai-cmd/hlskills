# 开发段流程

> 本技能的接收、候选和验收关卡是文档纪律，靠执行者核对证据；没有 runtime 强制。

接手 `hlpm` 已交接的产品包，按用户选择完成开发、交付或发布。单人从需求开始跑全流程时使用 [hl-flow](../hl-flow/SKILL.md)。各阶段由执行者核对交付证据。完成前运行相应验证，检查输出与退出码，保留失败或缺测的位置。

接收前由步骤 0 判定整个包是否可用。已接收后遇到局部歧义，只暂停该条款及依赖它的任务，把原条款与实测差异交产品；独立且已明确的工作继续。影响整包基线、候选身份或共享前置条件的阻碍须先解决。同一问题连续三次修复失败时，将证据和方案升级给用户决定。

按[角色加载方式](../SKILL.md#agent-使用方式)选用本阶段角色。规划由 `planner` 负责，架构和 ADR 由只读 `architect` 提供意见，`executor` 落盘和实施。审查、测试与验证分别由以下步骤中的角色留存实际结论。

## 开发段开发流程（15 步）

### 第零阶段：交付物验证

首次接手按[步骤 0 接收清单](handoff.md)核对版本目录、产品摘要、适用证据和状态。已接收的同一基线从记录处继续。适用项有缺口时将条款、证据、补件和复验要求填入[拒收单](handoff-rejection.md)，退回产品后按原定范围核验。

### 第一阶段：Git 与开发准备

1. **Git 工作区准备**
   - 检测当前环境（普通仓库 / 工作区）
   - 如在主分支，先创建 feature 工作区分支
   - 安装依赖并验证干净基线（运行现有测试确保通过）

2. **开发计划**（`planner`）
   - 按可独立验收的业务结果安排工作。一处共享逻辑即可满足需求时，用一项计划覆盖受影响的入口。
   - 每项关联 AC、受影响入口、验证命令或操作及预期。复用或修改已有实现时，写明真实符号、文件、调用方和选择理由。首次新增时，记录查过的范围、确认的契约、拟新增的位置及接入方。
   - 有前后依赖、跨团队或跨会话交接时，补上前置产物及位置、待接手工作与完成条件。遇到阻碍时标明受影响的切片。

3. **技术设计与架构决策**（`architect` 设计，`executor` 写入）
   - 按步骤 0 的分工完成开发侧承接的项目。数据设计按需定义表、字段类型与精度、约束及迁移。接口设计按需定义协议、请求响应、错误与兼容策略。将版本、BL/AC 与定义位置记入 `knowledge/tech-design.md`，供产品和测试按原编号复核。已有产品侧定义或项目契约引用原件，补充实现所需的技术细节。
   - 若不同方案会改变业务结果（如半天假扣减规则），标出 BL/AC、候选结果和受影响的操作，回产品确认后再定该部分技术设计。
   - 对关键技术选型以 ADR 格式记录到 `knowledge/adr/`
   - 接口设计遵循 `hlapi` 规范
   - 数据库迁移遵循 `hldb` 规范
   - 错误处理遵循 `hlerror` 规范

### 第二阶段：开发与审查

4. **开发**（`executor`）
   - 遵循技术设计文档、编码标准（`hlcode`）、API 设计规范、数据库迁移规范、错误处理规范、无障碍规范
   - **动手前**，`executor` 直接使用 [hlquality 开发约束](../hlquality/SKILL.md#开发时使用)和 [hlsecrets 开发约束](../hlsecrets/SKILL.md#开发时使用)。按本次读写路径选择质量规则，确认可复用的实现、凭证来源及验证方法。并行实现时把适用约束交给负责该改动的人。
   - **每次提交前**，对实际拟提交内容自检，覆盖暂存版本和本次要交付的新文件。直接交评时检查当前工作区的交付范围。用项目已有检查或针对性测试验证质量，按默认启用的凭证规则脱敏核查。确认引入硬编码凭证、违反验收条件或未通过项目必需检查时，先修复并复验。将检查范围、结果和待核项随改动交给评审。
   - 推荐 TDD，覆盖率 ≥ 80%
   - 独立的前后端或模块任务可交不同 `executor` 并行实施。
   - 有 UI 时，按确认原型的布局、字号、间距、资源和响应式规则复用项目组件，从同一组数据重走 TC 的实际操作，核对焦点、状态、失败恢复和最终反馈。列表与详情沿用同一对象及领域规则。原型的模拟响应用真实服务验证。设计和 PRD 对同一状态有分歧时，定位至 BL、控件和 AC，回到产品确认。

4.5. **按 PRD 逐项登记实现**（`executor`）
   - 每完成一条业务规则、状态机分支或非功能实现，随代码提交相应知识条目。在 `$VERSION_DIR/consistency-matrix.md` §5 按本版 PRD 的实际标题、BL/AC 记录实现文件与符号、实际实现 SHA、TC 和验证状态。SHA 可在同一 PR 后续提交，保留被引用的实现提交。
   - 用 `git log -p -- <路径>`、`git show <实现提交> -- <路径>` 核对行为差异。复用时引用原符号和基线；历史不可追时注明限制、候选代码位置与行为证据。
   - 测试报告记录真正运行的候选完整 SHA。步骤 8 后用 `git merge-base --is-ancestor <实现提交> <候选提交>` 核对归属。变基、拣选或解决冲突后重新定位实际实现并复测。
   - 尚未执行的项标待验，§6 的 N/A 沿用本期适用依据。发现偏离时附 PRD 条款与实际差异，越界功能立即交产品确认。小改沿用矩阵原行，额外勾选记录按需存放在同包 `code-checklist.md`。

5. **代码审查**（`code-reviewer`）
   - 按本库 [hlreview](../hlreview/SKILL.md) 独立审查本次差异。用开发自检记录定位改动，按 [hlquality](../hlquality/SKILL.md#规则清单) 复核适用规则及待核项。先查找变更路径适用的 AGENTS.md、CONTRIBUTING.md、CODING_STANDARDS.md 及已有实现，再按严重 / 重要 / 次要三级记录发现。涉及项目约定时注明规则来源。
   - 严重问题：依据当前变更的实际影响或项目强制门槛判定，记录证据，修复并复验后方可联调、合入。专项规则的原始等级随发现保留，合入决定使用本次评审结论。必需检查尚无证据时保持待验。
   - 重要问题建议修复，次要问题可选优化。
   - **🚨 审查意见 = advisory(v26 纪律)**:`code-reviewer` 的每条 finding 在接受前必须**逐条对照真实代码路径核实**(file:line 可定位、逻辑链可复走);对不上代码的臆测 finding → 直接拒绝并记录,不因"审查说的"就改代码
   - **复审上限 2 轮**:同一轮审查意见修复后最多复审 2 轮,防"审查→修改→再审"无限打磨;2 轮后仍有分歧 → 升级用户决策

6. **前后端联调**。按接口契约核对请求、响应和双方处理结果。

7. **前后端自测**（`executor`）。按本期用例从真实入口验证核心路径、接口和终态。

7.5. **★ PRD 走查**(`executor` + `code-reviewer` 联合，拦截错误实现 B + 范围越界 D）
   - **触发时机**：开发**完成后**，分支完成前
   - **操作**：对照 `$VERSION_DIR/consistency-matrix.md` 第 5 矩阵（代码实现追踪矩阵），**逐行核对代码实现**
     - 每行确认：实现状态（✅/❌/⚠️/➕） + 偏离说明（如有）
     - 输出**走查报告**：每行结果 + 偏离原因 + 修复计划
   - **走查不通过**：
     - ❌ 未实现 → 返回步骤 4 补齐 + **清空旧 SHA + 状态改为 ⚠️(待重审)**（防旧数据残留误判）
     - ⚠️ 偏离 → 返回步骤 4 重写 + **清空旧 SHA + 改为 ⚠️** + 触发强同步（v5 规则：不可豁免已通过的评审）
     - ➕ 越界 → 与产品段确认：保留则补 PRD / 移除则删代码
   - **走查通过**：进入步骤 8 记录候选
   - 小改沿用步骤 4.5 的矩阵，逐条对照步骤 7 的执行结果。发现未覆盖的适用规则时按上面的失败处理返工。

### 第三阶段：固定候选

8. **记录候选分支、基础分支和完整提交 SHA**。代码审查和步骤 7.5 均通过后，在该工作区完成后续安全检查、回归、适用的补充验收与生产审计。用户决定丢弃时，终止本版本的后续验收、发布和部署；清理仅限明确授权的对象。补测试或修复导致 SHA 变化时，换用新的候选并重新取得与其相符的必需验证结果。

### 第四阶段：测试与审计

固定候选后打开[步骤 9–12.7 测试与审计](verification.md)，核对安全性、产品用例及代码变体、用户路径、实现证据和知识库。重跑所需检查后按同一候选交付；缺测、失败和待补证分别列明。

### 第五阶段：交付与发布

通过适用验收后按[步骤 13–15.5 交付、发布与复盘](delivery.md)核对产物、完成标记、授权和实际发布证据。按[交付清单](delivery.md#交付文档清单开发段补充)记录本期产物、实际路径及负责人。业务逻辑改变时，同步受影响的接口、数据设计、测试、用户手册和帮助文档；需求口径变化交产品修订。

## 交接段

开发完成时将候选提交、测试与审计证据、实际产品包路径返回当前链路。用户只选择开发时在此交付。发布前取得用户授权并交给 hlrelease。部署时核对同一版本的远端发布记录、目标环境与部署授权。用户放弃候选或必需验证未通过时，返回具体状态并结束或等待修订。
