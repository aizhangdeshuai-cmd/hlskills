# 第四阶段：测试与审计

9. **安全审查**（`security-reviewer`）
   - 针对本次变更核对服务端资源归属、状态转换和适用的幂等边界。只读审查及项目既有测试记录允许、拒绝及拒绝后的数据状态。按本库 [hlsecrets](../hlsecrets/SKILL.md) 在固定候选上独立核查变更的源码、配置和注释，复核开发期留下的待核项及修复位置，全程脱敏。
   - 发现中区分已证实失败、缺证据、已通过，附候选 SHA 与修复后的验证位置。按 [hlreview 的生产审计](../hlreview/SKILL.md#生产审计) 处理高影响阻碍。

10. **测试用例编写(代码层面) + 执行 + 总库沉淀**（`test-engineer` 编写 + `qa-tester` 执行）
    - **用例来源分两层**:
      - **验收用例**(业务黑盒):来自 hlpm 交付的 `$VERSION_DIR/test-cases.md`(版本快照),直接执行,不重写
      - **代码层面用例**(白盒):`test-engineer` 基于**本次代码 diff** 补充编写,覆盖 hlpm 写不出的代码层修改点:
        - 内部 API/Service 异常分支(null 分支、超时、降级)
        - 数据库约束场景(唯一索引冲突、外键级联、乐观锁冲突)
        - 缓存失效/穿透/雪崩、消息队列重复消费/消费失败
        - 并发竞态(同一资源并发提交)
        - 实现选型边界(软删除开关、部分索引、事务原子性)
        - 本次重构涉及的函数/模块回归点
    - **交叉验证**：按 [hltest 的验收命令](../hltest/SKILL.md) 提供 `acceptance-plan.json`、产品交接记录中的 `plan_sha256` 与 `spec_sha256`、独立取得的候选完整 SHA 及运行报告，保留逐 TC 结果。计划发生变化时先核对产品修订。涉及服务端权限、取消或重试时，验证业务记录和写入次数。涉及多页面时，按访问顺序记录同一对象与每页结果。同角色的运行记录填 `page_visits`，跨角色填 `role_visits`。见[候选记录格式](../hltest/acceptance-reports.md)。
    - 执行全部用例(验收 + 代码层),验证一致性矩阵 §1 验收方法列(验收标准)全部通过
    - **沉淀到总测试库**:把验收用例(本期 hlpm 产出)+ 代码层用例(本步编写)+ 交叉追溯,合并写入 `knowledge/tests/{module}.md`(按 `hlkb` 第 9 类"总测试库"规范,模板 `hlkb/templates/code-tests.md`)。总库跨版本累计维护,标注引入版本(同 `knowledge/api/`、`knowledge/db/`)
    - **候选运行记录。** 保留产品已签核的 `$VERSION_DIR/test-cases.md` 作为验收依据。启动测试时把用例实际采用的计划与规格摘要写入 JUnit 或人工执行报告。用稳定 TC 在 `knowledge/tests/{module}.md` 关联代码测试及本期 QA 报告，结果和截图随实测提交存档。业务预期需调整时回产品段确认新修订。
    - 测试代码本身放项目语言约定的测试目录(Java `src/test/`、Node `test/`、Go 同级、Python `tests/`),随代码 commit 不另计入文档交付物
    - **反模式禁止**:不得"照着实现写用例"——代码的缺陷不能被当成正确预期写进用例。预期以 PRD 验收标准为准,代码偏离 PRD 时改代码不改用例

11. **按适用条件验证用户路径**（`qa-tester`）
    - UI 变更按 [hlbrowse](../hlbrowse/SKILL.md) 在候选上操作并保存断言、无障碍与视口证据。标有 `prototype_match` 的 TC 按[已确认原型](../hlpm/prototype-handoff.md#开发和-qa-如何比对)比较；有 `reference` 时另按[竞品要求](../hltest/acceptance-reports.md#竞品-ui-对照)复跑。纯 API / CLI 核对相应接口或命令结果。
    - 在生产审计和分支收尾前完成约定的独立 UAT、兼容性或压力测试，必要时调用 [hltest](../hltest/SKILL.md)。记录所测提交、测试范围与未测项；必需测试失败、缺失或仍在运行时暂停放行。

12. **生产审计**（`verifier`）
    - 先在步骤 12.5 核对每条适用规则的实现证据，再按本库 [hlreview](../hlreview/SKILL.md) 的“生产审计”核对同一版本的授权、数据、运行、恢复及关键用户路径证据。
    - 输出发布准备度（0–100，越高越接近可发布）、证据、阻碍项及待接受的风险。按 hlreview 给定的区间与分数上限判断；必需 CI、回归或 UAT 失败或未完成时暂停放行；另有准备度低于 50 或确认的发布阻碍时也需阻塞。QA 健康度与发布准备度分别记录。范围或版本无法确认时记“证据不足，暂不评分”，补齐后复审。

12.5. **★ PRD 覆盖率审计**(`verifier` 主导，拦截非功能漏实现 C + 兜底 A/B/D）
   - **触发时机**：生产审计**前**，上线前最后一道关卡
   - **操作**（人工 + 矩阵双轨）：
     - **主方式**：以产品基线的适用 AC 为分母，对照第 5 矩阵中的实现位置和候选报告中的全部关联 TC。某 AC 漏行或仍有必测场景失败、跳过、缺测、证据失效时，将该 AC 和对应 TC 列入差异清单。
     - **辅助线索（可选）**：可用 Grep 搜索关键词（如状态名 / 业务规则名）定位候选实现位置；正则/搜索结果**仅作线索，不作"已实现"判定依据**
     - **不依赖**：纯正则匹配控制流关键字（`if` / `switch` / `case`）作为"已实现业务规则数"的统计——这种推断不可信，因注释/字符串/任意控制流都会匹配上
   - **覆盖率要求**：
     - 核心模块（订单 / 支付 / 安全）：**100%** = "每条业务规则必须经 `verifier` 在一致性矩阵第 5 矩阵标注 ✅ + **人工复核签字**(产品经理或安全工程师)"。单一自动化检查不构成 100% 通过——LLM 没法机械判定"某条规则算不算核心模块",**最终判定依赖人工签字**
     - 一般功能逐项记录结果，≥ 95% 为参考指标。缺少必测证据或有未解决的阻断时暂停放行。
     - 工具类与边缘功能沿用项目的覆盖率指标，所有已约定的必测场景仍须通过。可重复的行为直接复核同一候选的有效运行记录。人工集中在需求歧义、视觉判断、无法自动取证的行为及规定的签核。
   - **硬性覆盖要求未满足或仍有阻断项时**:
     - 输出**差异清单**(每条:PRD 条款 / 实际状态 / 修复建议)
     - 强制返回步骤 4 补齐,**不能发布**
     - **3 轮回退上限**:连续 3 次不达标必须升级到用户决策(避免与 7.5 / 12.5 死循环)
   - **提交步骤 12 的证据**：记录模块覆盖率、签字与差异清单。由步骤 12 按 hlreview 的准备度区间统一评分。保留本步骤已有的覆盖率关卡。
   - 核心模块按实际影响确定。例如仅调整两条退款规则，权限和状态转换均需分别追到对应实现、候选提交的测试结果及实际人工复核。

12.7. **🚨 项目知识库完整性自检**(`executor` 主导, **应阻塞发布**)
   - **触发时机**: 步骤 12.5 和 12 完成后，步骤 13 交付验证前
   - **检查清单**(按本版变更核对适用项，不适用项记录原因):
     - [ ] `knowledge/api/{module}.md` 覆盖本版本所有新增/修改/删除接口(URL / Method / 入参 / 出参 / 错误码 / 权限)
     - [ ] `knowledge/db/{table}.md` 覆盖本版本所有新增/修改/删除表 + 字段(与 `migrations/` SQL 一致)
     - [ ] `knowledge/db/er-diagram.md` 反映最新表关系(如有外键变化)
     - [ ] `knowledge/adr/{NNNN}-{slug}.md` 含本版本所有重大决策(如本版本新增了 1 个 BL-N 3 方案选 1 个, 必有 ADR)
     - [ ] `knowledge/state-machines/{entity}.md` 反映最新状态机(本版本新增/删除状态/转移)
     - [ ] `knowledge/enums/{enum}.md` 覆盖本版本所有新增/修改枚举值
     - [ ] `knowledge/error-codes/README.md` 含本版本所有新增/修改错误码
     - [ ] `knowledge/dependencies/README.md` 与 `pom.xml` / `package.json` 一致
     - [ ] `knowledge/env-vars/README.md` 含本版本所有新增/修改环境变量
     - [ ] `knowledge/tests/{module}.md` 含本版本验收用例 + 代码层用例 + 交叉追溯(每个新增/修改的 Service/API 有测试点 + 对应 AC + 测试代码路径,无 ⚠️ 待补)
     - [ ] `knowledge/pitfalls/` 含本版本修复 bug 的根因沉淀(如有 bug 修复;v32,hlbug 步骤 14 强制项)
     - [ ] `knowledge/prd.md` 含本版本章节(如 v3 章节)
     - [ ] `knowledge/glossary.md` 收录本期新增或调整的业务术语
     - [ ] 本期执行过 hlpm 时，按实际包路径核对 `version.py retro` 所列复盘里的产品段信号。开发段信号在交付验证通过后由步骤 15.5 写入
     - [ ] `knowledge/tests/` 含本版本章节
     - [ ] 步骤 0 记录的当前宿主约束文件与本期实际变更一致
   - 接口、表结构、业务规则和测试映射等事实发生变化时，对应知识条目与主文档随实现同次提交。矩阵中的实现 SHA、候选运行报告及截图在提交产生或验收执行后登记，可在同一 PR 的后续提交补入。交付时按步骤 4.5 核对实现提交与实测候选的关系；若随后修改代码或测试，按步骤 8 更新候选并复验。
   - **失败处理**: 任一缺失 → 应阻塞步骤 13 交付验证 + 步骤 4.5 重新走(靠 Agent/用户把关, 非机制强制阻断; 与 `hlkb` 能力边界声明一致)
   - **详细规则**: 详见 `hlkb` 技能 SKILL.md §同步触发表
