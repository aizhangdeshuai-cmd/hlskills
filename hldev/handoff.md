# 第零阶段：交付物验证

0. **★ 验证版本目录 + 8 项交付物 + 一致性矩阵**（`executor` 主导，阻塞点）
   - 初始化或复用当前宿主的项目约束文件，记下实际路径。Claude Code 使用 `CLAUDE.md`，Codex 使用 `AGENTS.md`，Cursor 使用 `.cursor/rules/*.mdc`。多宿主项目沿用选定的规则。已存在时只补缺项；创建时按 hlkb 约定去除全局文件已覆盖的规则。
   - 从 hlpm 交接单取得实际版本目录、UI、截图、竞品三个适用条件和设计页面清单。从项目根运行本库 `python3 "$HLPM_DIR/version.py" list .` 枚举包，再用 `python3 "$HLPM_DIR/version.py" resolve . "$SELECTED"` 解析所选包。将成功输出的绝对路径保存为 `VERSION_DIR`；同号时传明确路径（例如 `docs/v2`）。后续示例中的版本文件均相对于这个目录。仅有编号且有歧义时先澄清。
   - 归档或已完成的包结束。被拒收的包按拒收单复验，已接收的包核对原基线后续做。按[交接检查](../hlpm/handoff-package.md)运行接收检查，传入产品交接记录的 `--spec-sha256 "$HANDOFF_SPEC_SHA256"`，核对输出的 `plan_sha256` 与产品留存值。保留两项原始摘要和已批准的包供步骤 10 使用。旧包先补齐来源和计划，文件盘点成功只记录到盘点栏。

   ```markdown
   ## 产品交付物验收

   - [ ] 实际版本目录与上游交接一致，已核对该目录中的状态和既有拒收原因
   - [ ] 五项必出齐全；三项条件出有证据或不适用依据；组件与流程图的子目录已纳入
   - [ ] 补交包已逐项复验，拒收单保留了原因与修订依据

   ### 版本一致性（必查）
   - [ ] PRD 版本：vX
   - [ ] 设计版本：vX（不涉及设计时 N/A）
   - [ ] 用例版本：vX
   - [ ] 所有适用文档版本号匹配

   ### 一致性矩阵（必查）
   - [ ] 一致性矩阵存在
   - [ ] 业务规则覆盖矩阵完整
   - [ ] 适用的状态机覆盖矩阵完整；无状态变更有依据
   - [ ] 适用的权限覆盖矩阵完整；权限范围有依据
   - [ ] 非功能需求覆盖矩阵（性能 / 安全 / 兼容 3 个子表）完整
   - [ ] 不一致清单为空或已闭环
   - [ ] 适用项逐条指向实测证据或有效评审结论；不适用项有本期范围依据；仍缺内容、证据或存在未决阻碍时退回补齐

   ### 自检报告（v6 必查）
   - [ ] 自检报告存在（`$VERSION_DIR/handoff-self-check.md`）
   - [ ] 自检报告与 handoff-package.md 自检清单勾选一致
   - [ ] 自检记录列出实际评审者或免审、不适用的原因，结论可回查

   ### 产品交付物自检（设计及截图项按适用条件检查；用户跳过评审时核对留痕）
   - [ ] 标准 PRD 核对目标、范围及适用功能卡。迭代 PRD（含既有 Mini PRD）核对基线、行为差异、受影响入口及回归范围。按[产品段选型](../hlpm/SKILL.md#启动与选版)接收实际文档。
   - [ ] 从受影响 BL 找到验收表及 TC。分册版从 PRD 附录领取同版 `acceptance-criteria.md`，按其中的范围及通过条件核对。有未确认需求时核对其影响。UI 变更核对字段、控件、状态反馈与原型入口。未变的约定按文中引用回查基线。
   - [ ] 分别核对数据、接口的编写方。产品侧写的从附录打开各自的 Markdown 分册，核对约定版本与 BL/AC。开发侧写的核对业务依据与可验证结果，满足即可接收并转步骤 3。旧包沿用既有分工；本期无关的项按范围跳过。
   - [ ] 逐项核对适用的业务、流程、数据、状态、权限和非功能要求；埋点及原型截图仅在适用时验证
   - [ ] PRD 的关键条件、业务字段含义与预期可验证，实际评审或免审有记录。按[产品接收范围](../hlpm/handoff-package.md#开发与测试的接收范围)核对上线行为。若假设影响实现或旧条款混入演示操作，标出受影响编号交产品厘清。
   - [ ] 有 UI 时从 PRD 链接实际操作。要求按确认原型还原时，核对确认记录、视口、样式资源和该 TC 的 `prototype_match`，依[原型交接](../hlpm/prototype-handoff.md)接收同一版本。
   - [ ] 测试用例覆盖适用的业务规则、状态机、权限；已记录实际评审或免审
   - [ ] 一致性矩阵 §1 验收方法列每条可验证(AC-NNN 编号齐全)
   - [ ] 核对非功能指标的来源、适用性及待测项；沿用既有指标时提供出处
   ```

   - **🚨 设计稿搬移白名单(硬性)** — 设计稿 HTML 中含有"设计元信息"(用于评审),搬到生产代码时**必须剔除**。**完整白名单(DOM 排除/属性排除/CSS 排除/保留 + 5 区块扩展识别)见 `hldesign` 技能 §设计与实现分离(单一可信源),本段不重复定义**。冲突时以 `hldesign` 为准。

   - 适用项全部通过、豁免有依据后，由执行者运行 `python3 "$HLPM_DIR/version.py" mark "$VERSION_DIR" accept` 记录接收，再进入步骤 1。
   - **任一 ❌ → 填写 `handoff-rejection.md`（拒收原因 + 不符合项）→ 退回产品段**
     - 接收前将原因追加到 `$VERSION_DIR/handoff-rejection.md`，执行 `python3 "$HLPM_DIR/version.py" mark "$VERSION_DIR" reject`。已接收后发现歧义，暂停受影响的切片，向产品提交原条款、实测差异与待决定事项。若确认原约定，按原包修实现；若变更需求，由产品另建版本并关联旧包，重新交接。
   - 拒收原因分类（v5）：
     - 缺失（产品漏交某项）
     - 不达标（PRD 模糊字眼 / 设计违反规范 / 用例覆盖率低 / 非功能需求缺指标）
     - 内部矛盾（文档间冲突）
     - **三项不一致**(版本号不匹配 / 一致性矩阵有 ❌）
