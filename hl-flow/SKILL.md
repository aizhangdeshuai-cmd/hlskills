# 新需求开发流程

> ## ⚠️ 能力边界声明
>
> 本技能"硬性关卡/强同步/会签"是**文档纪律**,靠 Agent 自觉 + 用户手动打断,**非** Claude Code runtime 强制(漏一步不自动阻断;Agent 模型弱或 prompt 冲突时关卡可能失效,需手动打断重读)。详见 `README.md` 「⚠️ 能力边界声明」。


## 通用纪律：完成前验证
> **路径规范**：本文件涉及的 `knowledge/` 路径命名遵循 `hlpm/path-conventions.md` 中央规范（命名/深度/特例）。


**任何阶段标记"完成"前，必须执行以下验证规则：**

- 识别能证明该阶段完成的验证命令，完整运行该命令
- 读取完整输出并检查退出码，确认通过后方可声明完成
- **绝对禁止**："应该通过了"、"看起来正确"、"之前检查过了"、"应该没问题"、"可能没问题"
- **铁律**：证据先于断言，无一例外。未经新鲜验证证据，不得声称完成

### 受阻停止纪律
- 遇到阻塞时暂停受影响的步骤和依赖任务。整包基线、共享前置条件或候选身份有问题时，暂停整段交接；其余已明确的独立工作可继续。
- 向产品经理（`analyst`）报告阻塞情况
- 产品经理无法解决时，立即向用户提问
- 3 次修复尝试失败 = 质疑架构方案，不尝试第 4 次变体修复

## 角色与 Agent 映射

按[角色加载方式](../SKILL.md#agent-使用方式)读取本技能所在仓库中本阶段需要的角色。

| 角色 | Agent | 用途 |
|------|-------|------|
| 产品经理 | `analyst` / `planner` | 需求分析、任务规划与分配、流程统筹 |
| UI/UX设计师 | `designer` | 界面设计、交互设计、设计评审 |
| 前端开发 | `executor` | 前端页面与组件开发 |
| 后端开发 | `architect` / `executor` | 后端架构设计与API开发 |
| 代码审查 | `code-reviewer` | 代码质量审查 |
| 安全审查 | `security-reviewer` | 安全漏洞扫描 |
| 测试 | `test-engineer` / `qa-tester` | 测试用例编写与执行 |
| 验证 | `verifier` | 交付前最终验证 |
| 用户（我） | — | 关键节点确认者，未确认不得进入下一阶段 |

## 新需求开发流程

### 第零阶段：加载项目上下文
0. **加载已有文档** — 在分析新需求之前，**先读取项目已有知识**，避免重复分析：
   - 接续任务时从 `.hl/memory/working.md` 取当前进度和原文指针。用业务名、模块或 BL/AC 编号按 [hlkb](../hlkb/SKILL.md) 检索已有知识。
   - 按命中位置核对相关 PRD、技术设计、ADR 或竞品章节；涉及某一历史版本时，打开对应版本包。
   - 📎 迭代需求场景：**必须先理解项目现状，再分析新需求**。跳过此步会导致脱离上下文
   - **项目约束文件初始化**:检测项目根 AI 约束文件(Claude Code→`CLAUDE.md` / Codex→`AGENTS.md` / Cursor→`.cursor/rules/*.mdc`;多宿主时沿用本任务选定的规则路径，无法判断时先确认宿主)。不存在 → 按 `hlkb/templates/claude-md.template.md` 创建;已存在 → 校验是否含 `## 🚨 完成前自检` 段,缺则追加该段(不重写其他)。详见 `hlkb` §项目约束文件。

### 第一阶段：需求阶段
1. **需求分析** — `analyst` 基于已有文档上下文，理解并梳理新需求，如用户提供需求文档（含图片）：
   - 使用 Read 工具读取文本内容
   - 📸 **分析文件中的图片**：优先用模型原生多模态能力识别图片中的界面草图/流程图/参考截图/架构图；不支持则用 Read 工具读取（支持 PNG/JPG/WebP/PDF）
   - 将图片内容与文字需求合并分析，形成完整需求理解
   - 沿用 [hlpm 需求澄清](../hlpm/SKILL.md#需求澄清)中确认的范围，记录本次是否涉及 UI、页面布局或浏览器交互。已有明确范围时直接复用。纯后端、CLI 或 API 改动在 PRD 中记录不涉及设计的依据，步骤 4 后直接进入步骤 8。
   - 按[需求澄清](../hlpm/SKILL.md#需求澄清)核对本期规则。已有明确依据的直接引用，其余疑问集中向用户提问并等待。所有疑问已确认或由用户明确移出本期，才按确认后的范围编写 PRD、制作原型和编验收用例。后续发现新的本期疑问，暂停这些产出并返回本步。
2. **竞品调研与参考。** 单一竞品的指定交互按[竞品 UI 还原](../hlpm/competitor-ui.md)采集来源并关联 TC。新项目需要品类与市场比较时，按本库 [hlresearch](../hlresearch/SKILL.md) 调研，由 `analyst` 核对来源、比较口径与假设，主代理根据项目目标形成建议：
   - 识别直接竞品与间接竞品
   - 分析竞品核心功能、差异化优势、定价策略
   - 输出竞品分析报告，明确自身产品定位与差异化方向
   - **从 `/hlpm` 导入时**，复用已有调研和用户决定。已有 PRD 经步骤 1 核实本期疑问已收口，可直接进入步骤 4。旧稿中的未决规则仍在本期时，先澄清再修订。
3. **PRD编写** — `analyst` 生成 PRD 正文，由主代理或调用方写入选定版本。从 hlpm 导入已有需求文档时直接评审。
4. **PRD 评审。** 从本期行为差异、真实入口和调用方确定影响项。用当前技能目录的 [review_roles.py](review_roles.py) 运行 `python3 "$HL_FLOW_DIR/review_roles.py"`（`HL_FLOW_DIR` 为本文件所在目录），有影响时追加 `ui`（页面或交互）、`authorization`（权限边界）、`migration`（数据迁移）、`architecture`（架构）、`accounting`（跨角色记账）或 `cross-team`（独立团队接手）。同一会话可承担所需视角，评审结论记入已有迭代卡。
   - 常规小改由产品和测试核对旧行为、新行为、受影响入口及回归。例如 API 缺省每页 20 改 50，用实际入口分别验证缺省返回 50、显式传 20 仍返回 20。
   - 按输出的其余角色复核受影响部分。`formal_handoff` 为真且任务进入开发时，复用 [hlpm 的正式产品包](../hlpm/handoff-package.md)，让产品、开发与测试核对同一组 AC、TC 和版本证据。员工申请、主管审批分别会冻账和结算时，加入跨角色复演。只交 PRD 或原型的任务仍停在用户选定的终点。
5. **UI/UX设计（涉及 UI 时）** — `designer` 交付产品原型及其资源。已有本期确认原型时直接按[原型还原依据](../hlpm/prototype-handoff.md)核对相应任务与状态。需要新设计时按[步骤 6a.1 核对规范](../hlpm/design-stage.md#6a1-核对规范)，复用项目组件、状态管理、路由和布局。无规范和参考页面时，先确认风格、色彩与响应式方向。
   - 依约定视口和状态并排核对文字、控件、表格、表单、弹窗、间距和图标。
   - 从 PRD 的 AC 预分配 UI 场景的 TC，依据[原型验证](../hlpm/design-stage.md)在浏览器操作，按页面顺序核对对象、可见状态及异常反馈。步骤 8 沿用场景编号与实测记录。
   - 记录获准差异的位置和原因，修复本期依据要求一致的项目，再交设计评审。
6. **设计评审（涉及 UI 时）** — `designer` 主持，沿用步骤 4 确定的影响与角色，核对适用项：
   - `designer`（UI/UX）— 主持 + 设计规范一致性
   - `analyst`（产品）— 需求覆盖度与优先级对齐
   - `executor`（前端）— 前端实现可行性与组件复用
   - `architect`（后端）— API/数据接口对齐
   - `test-engineer`（测试）— 交互状态覆盖 + 无障碍 WCAG 2.2 AA 检查
   - 设计师记录影响实现或验收的意见与决定。涉及业务取舍的分歧由产品或用户裁定。
7. **用户确认设计** — 从 PRD 的演示入口走到业务结果，提交本版设计供用户确认。要求据此还原前端时，按[原型交接](../hlpm/prototype-handoff.md)将相应 TC 与获选版本绑定。沿用已确认且未变的设计时引用原记录。无 UI 时直接进入测试准备。

### 第二阶段：测试准备
8. **测试用例编写** — 从已确认的用户约束和 AC 列出本期必测 TC。沿用 [hlpm 的验收计划格式](../hlpm/handoff-package.md)，在本次交付目录冻结 `acceptance-plan.json`，已有产品包时直接复用。UI 场景注明实际页面，纯 API 或 CLI 留空。
9. **用例评审** — `test-engineer` 与 `analyst` 核对每个场景的前置条件、输入和预期。沿用产品包时传递原交接记录中的两项摘要；独立运行时按 [hltest 报告说明](../hltest/acceptance-reports.md) 保存评审通过的计划摘要，供步骤 20 比对。

### 第三阶段：开发阶段
10. **Git 工作区准备** — 创建隔离工作区进行开发，避免污染主工作区：
    - 检测当前环境（普通仓库 / 工作区）
    - 如在主分支，先创建 feature 工作区分支
    - 安装依赖并验证干净基线（运行现有测试确保通过）
11. **开发计划** — 沿用 [hldev 的开发计划](../hldev/SKILL.md)。每项关联 AC、已有符号与改动位置、受影响的入口、复用理由、验证命令及预期。一个改动可以覆盖多个入口，跨团队或跨会话时补上依赖与接手条件。
12. **架构决策记录** — 对关键技术选型以 ADR 格式记录到 `knowledge/adr/NNNN-<slug>.md`（4 位编号，详见 `hladr`）
13. **开发** — `executor`（前端+后端）开发，遵循技术设计文档、编码标准、API设计规范、数据库迁移规范、错误处理规范、无障碍规范。推荐使用 TDD，覆盖率 >= 80%
    - **并行策略**：前端和后端任务如无依赖关系，可并行分派执行
    - 多个独立模块的任务可同时分派给多个 `executor` 实例并行推进
14. **代码审查** — `code-reviewer` 审查代码质量，按严重/重要/次要分级输出
15. **联调** — 按实际调用关系联调，涉及前后端时对接接口，纯 CLI 按命令与其依赖验证。
16. **开发自测** — 按 PRD 的输入、输出和边界验证功能完整性。
17. **记录待验版本** — 记录本次候选提交和基础分支，保留工作区完成后续检查。用户选择丢弃时结束此次流程。

### 第四阶段：测试
18. **安全审查** — `security-reviewer` 执行安全漏洞扫描
19. **测试用例测试** — `qa-tester` 按用例执行测试（单元+集成+E2E）
20. **场景验收** — UI 在 TC 的约定视口操作到最终结果。以确认原型为实现依据时，提交同一基线与候选的对照报告。有竞品要求时另核对竞品来源。纯 CLI 核对命令输出与退出状态，纯 API 核对响应及数据断言。按 [hltest](../hltest/SKILL.md) 核验计划、候选提交及报告。约定的用例缺失、跳过、失败或证据不可用时，列出编号并暂停放行。
21. **生产审计** — `verifier` 按本库 [hlreview](../hlreview/SKILL.md) 核对实际部署证据并报告准备度（分数越高越接近可发布）。必需检查失败或证据不足时暂停放行，记录阻碍与对应提交

### 第五阶段：交付与发布
22. **交付验证** — `verifier` 对同一候选提交核对文档与功能。适用的安全、回归、UAT 和生产审计通过后，按用户选择合并、推 PR 或保留；合并产生新的发布提交时核对其 CI 证据。
23. **交付** — 按本期范围交付适用文档，在清单注明其余项的不适用原因。保存到项目目录：
    - `knowledge/` → 需求文档/PRD/技术设计/ADR/测试用例/回滚方案
    - `CHANGELOG.md`（项目根目录特例，业界惯例）→ 变更日志
    - `knowledge/design/` → 涉及界面设计时的规范和设计 HTML
    - `knowledge/user/` → 用户操作手册/帮助文档
    - 🚨 如不确定项目根目录，向用户提问确认
24. **用户确认发布** — 🚨 **硬性关卡**：向用户展示版本号/变更日志/预发布清单，用户确认后方可推送标签。严禁自动发布
25. **发布** — 用户确认后依 [hlrelease](../hlrelease/SKILL.md) 核对含版本与日志的提交、实际 CI 和远端标签，生成部署交接记录。
26. **用户确认部署** — 🚨 **硬性关卡**：向用户展示部署策略/目标环境/版本号/回滚方案，用户确认后方可部署。严禁自动部署
27. **部署** — 用户确认后按 [hldeploy](../hldeploy/SKILL.md) 将已验证的发布版本部署到指定环境，执行健康检查。

## 问题升级机制

- 各阶段遇到问题，由**产品经理**（`analyst`）组织会议讨论
- 会议中无法达成一致的问题，**立即向用户提问**，不得自行裁决
- 直至所有参与方无异议后，方可进入下一阶段

## 变更传播规则

当用户在"确认设计页面"阶段提出修改时，**所有关联文档必须同步更新**，产品经理负责追踪变更。

|---|------|-----------|------|
| 1 | 需求文档 | `analyst` | 原始需求描述与业务背景 |
| 2 | 竞品资料 | `analyst` 核证，主代理交付 | 品类调研交付比较报告；指定交互还原交付关联 TC 的参考证据 |
| 3 | PRD文档 | `analyst` 起草、主代理写入 | 产品需求详细规格说明 |
| 4 | 设计规范文档 | `designer` | 涉及 UI 时提供本期适用规范或既有规范的引用 |
| 5 | 设计HTML | `designer` | 涉及 UI 变化时提供可预览的交互设计稿 |
| 6 | 技术设计文档 | `architect` 设计、`executor` 写入 | 接口文档 + 数据库设计 + 逻辑架构图 |
| 7 | 架构决策记录 | `architect` 设计、`executor` 写入 | ADR 格式记录到 `knowledge/adr/NNNN-<slug>.md` |
| 8 | 测试用例 | `test-engineer` | 功能用例/边界条件/异常场景/E2E |
| 9 | **用户操作手册** | `writer` | 按使用者与变更提供；可复用 CLI 命令示例，涉及 UI 时附相应截图 |
| 10 | 帮助文档 | `writer` | 常见问题/故障排查 |
| 11 | 变更日志 | `planner` 整理、`executor` 写入 | 根据实际提交更新仓库根目录 `CHANGELOG.md` |
| 12 | 回滚方案 | `architect` 设计、`executor` 写入 | 本次发布的回滚步骤与验证方法 |

### 用户操作手册生成指引
`writer` 编写用户操作手册时：
- 📸 截图标注：优先用模型原生多模态分析页面截图，标注操作步骤序号和箭头
- 🎬 操作视频：可选，按 [hlmedia](../hlmedia/SKILL.md) 在本地录制、剪辑并核验演示片段
- 📖 结构：快速入门 → 核心功能操作 → 常见问题 → 故障排查
- 🧪 验证：每条操作步骤必须实测可复现
