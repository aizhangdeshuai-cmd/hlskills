# 只读代码审查

根据调用方给定的变更目的、版本和关注范围，对实现给出可核实的意见。可由不同审查者并行承担规范轴与需求轴，也可以由同一审查者顺序检查并各写结论。独立批准需要由未编写该变更的审查者给出。

1. **核对范围。** 对 PR 确认基线与待评审提交并查看共同祖先以来的 diff。对工作区结合 HEAD、暂存区、工作树及任务中的未跟踪文件。对片段或指定文件记录可见边界。阅读适用的项目规范、修改位置与调用方。
2. **规范轴。** 对照实际项目惯例检查错误传播、边界值、资源释放、并发与重试、可维护性以及依赖影响。以调用方可观察的后果或明确规则说明问题。
3. **需求轴。** 逐项对照验收标准，找出实现遗漏、偏离和意外引入的行为。指出验证行为的测试和仍未覆盖的路径。需求缺失时标记该轴待验证，继续检查可判断的部分。
4. **验证。** 使用项目已有的测试、类型检查、构建或审计结果，注明命令、版本、结果和覆盖范围。保持工作树只读；需要构建产物时选择隔离的临时输出。凭证检查仅输出位置和脱敏描述。
5. **汇总。** 每条意见记录位置、触发条件、证据、实际影响、可信度、修复方向和回归检查。专项规则记录其编号及原始严重度。汇入 hlreview 时另按本项目验收条件和实际后果评定严重、重要或次要，并写出是否阻断合入及依据。必需门槛缺证据时标记待补证。同源问题合并。

## 专项范围

- API 变更核对既有调用方、兼容性、版本、错误语义和契约文档。
- 样式审查依据项目格式和 lint 配置，标出具体规则和可用的只读检查命令。
- 性能审查检查输入规模、重复 I/O、数据库查询数、资源生命周期、缓存失效和关键路径开销，有实测时给出方法和结果。
- 安全审查检查身份和资源归属、输入与输出边界、参数绑定、日志脱敏与依赖风险。
- 上线准备关注回归覆盖、监控、回滚及未验证的关键路径。宿主提供第二审查上下文时可请求独立意见；用户要求的独立签核须记录参与者和结果。

## 审查结论

分别列出两轴的覆盖范围、发现和遗漏，再给结论。存在已确认的阻碍项时为 REQUEST CHANGES。已独立审查、所需证据齐全且没有阻碍项时为 APPROVE。仍缺需求、验证、独立签核或仅能提供局部意见时为 COMMENT，指出如何补足证据。如确有证据，可保留值得延续的做法。
