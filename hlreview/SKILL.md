# 项目评审与审查

从用户指定的范围开始。单独请求审查时交付发现与建议；修复、提交、发布由对应工作流在用户授权的范围内处理。文中角色定义和专项规则都随 hlskills 分发，使用技能时按本文件真实路径解析相对链接。角色版本与适配依据见[维护记录](references/upstreams.md)。

## 选择审查对象

| 对象 | 角色 | 核心问题与交付 |
|---|---|---|
| PRD | [analyst](../agents/analyst.md)、[architect](../agents/architect.md) | 核对业务规则、约束、边界和可验证的验收条件，给出通过、修改建议或驳回。 |
| 设计 | [designer](../agents/designer.md)、[executor](../agents/executor.md) | 核对状态、交互、无障碍与实现可行性，给出通过、修改建议或驳回。 |
| 用例 | [test-engineer](../agents/test-engineer.md)、analyst | 把关键规则和异常路径对应到预期结果，给出通过、修改建议或驳回。 |
| 缺陷修复方案 | architect、executor | 对照预期行为、根因证据和可验证的修复范围。 |
| 代码和配置变更 | [code-reviewer](../agents/code-reviewer.md) | 分别审查项目规范和需求实现，最后给出是否可合并。 |
| 安全相关变更 | [security-reviewer](../agents/security-reviewer.md) | 审查信任边界、访问控制和敏感信息，列出依据、影响与修复方法。 |
| 上线准备 | [verifier](../agents/verifier.md) | 给出准备度、发布阻碍、缺失的证据及下一项验证。 |

## 代码审查

1. **固定范围。** 分支审查记录基线与当前提交，确认引用可解析，用 `git diff <base>...HEAD` 对照共同祖先。审查工作区时记录 HEAD，使用 `git diff HEAD` 并从 `git status --short` 补看属于任务的未跟踪文件。局部审查或非 Git 输入记录文件、版本或片段边界。无变更、引用无法解析、输出截断和部分未读分别说明。
2. **组装审查材料。** 给审查者同一组路径、变更目的、影响范围和已有验证记录。规则来源优先读目标项目适用的 AGENTS.md、CONTRIBUTING、CODING_STANDARDS、lint 配置和相邻实现；需求来源取用户指定的验收条件、关联 issue 或该版本的 PRD。记录使用的文件和章节。范围外的外部链接只在具备访问权限时查看。
3. **规范轴（Standards）。** 对照项目规则、接口调用方和行为证据。关注错误吞没、重复读写、异步竞争、条件分支里的副作用、查询和资源生命周期。每条意见指明违反的约定或会产生的实际后果。对含义模糊的命名、重复逻辑、跨文件散落修改或提前引入的抽象，根据项目约定核实其影响，避免重复列出 lint 已覆盖的建议。需要系统排查时可读本库 [hlquality](../hlquality/SKILL.md)。
4. **需求轴（Spec）。** 从每条适用验收条件追到实现、边界分支和测试。分别记录满足、遗漏、偏离及额外改变的行为。缺少可信需求依据时注明“需求轴未验证”，可继续完成规范轴。
5. **汇总结论。** 有独立上下文时分别交给只读审查者；单一会话可以依次审查并注明执行方式。收回并标注两个轴各自的结论，同一根因合并为一条。请求只覆盖一个轴时注明范围。先列会改变合并决定的问题，再列待验证项和未检查的内容。

每条发现给出 **文件与行号、触发条件、可见影响、改进方向和验证方法**。来自专项检查的发现保留规则编号、原始等级。另评合入影响：已经证实违反强制项目门槛、破坏约定行为或造成严重风险，列为“严重／阻断”并给出依据；其他实际问题按影响列为“重要”或“次要”。缺少必需验证时标“待补证”，写出核验方法。汇总为“可合并 / 需要修复 / 证据不足”，注明覆盖范围。

## 安全审查

- 从变更入口追踪调用者身份、授权判定和目标资源归属。对涉及数据库、文件、页面输出及模型输入的边界，核对参数绑定、路径限制、输出编码和不可信输入处理。
- 对源码、配置、构建产物和日志，按本库 [hlsecrets](../hlsecrets/SKILL.md) 检查敏感信息。在报告中只记位置、类型和暴露途径。若范围包括 Git 历史，可在仓库内按提交定位，保持搜索结果脱敏。
- 检查依赖锁定和项目已有的审计结果、CI 权限、凭证注入与部署权限。记录依赖告警使用的数据源及日期；没有可用数据库时标注覆盖缺口。
- 用代码、配置、访问矩阵和现有的隔离测试验证。按影响和可达性解释风险，给出修复位置和防回归断言。报告确定问题与待确认项。

## 独立复核

认证、支付、权限、跨模块重构和紧急发布可以请求第二意见。先固定审核对象与尚有争议的问题。在宿主提供独立上下文且任务允许时，让另一只读审查者根据相同材料独立判断，再比较双方对同一条事实的证据。记录实际角色、上下文是否独立，以及宿主提供的模型信息。只有确认另一模型确实参与才标为“跨模型复核”。复核无法执行或中途失败时，记录具体原因，交付本次本地审查并列出需要第二人回答的问题。原流程或用户将独立签核设为必需时，保留该项未完成状态。

## 生产审计

核对拟发布版本、目标环境、关键路径和失败后的恢复方式。把以下证据与同一提交或产物对应。

| 维度 | 检查证据 |
|---|---|
| 访问与数据 | 敏感资源的授权测试、配置与日志脱敏、数据迁移策略、备份与恢复验证。 |
| 交易与回调（适用时） | 核对业务操作号、重试幂等和对账记录，检查“写入成功、响应丢失”后只有一次业务效果的测试。重放条件见 [hlerror](../hlerror/SKILL.md)。 |
| 运行与恢复 | 构建与 CI 结果、健康检查、报警、发布负责人、回滚办法及其演练证据。 |
| 用户关键路径 | 核心用户旅程的端到端结果，以及空、错、拒绝访问等状态的表现。 |

先判定必需条件。确认敏感资源的服务端授权失效、实际凭证暴露、同一交易发生重复写入、必要迁移不安全或高影响发布缺少必需的恢复路径，列为发布阻碍。记录受影响条件、脱敏依据、修复及复测结果。必需 CI、关键路径或约定的 UAT 失败同样受阻。尚未执行、报告缺失或候选不符，记“待补证，暂停放行”。修复后在最终候选上重新核对。

证据齐备后再评准备度。0–49 受阻，50–69 有风险，70–84 可在接受剩余风险后发布，85–100 证据充分。有已确认阻碍时归入受阻区间。候选或范围无法确认时暂不评分。另列 QA 健康分、待处理事项以及项目所需的发布确认。

## 接收意见与复核

逐条将意见映射回实际代码、项目规则或验收条款，记录“接受 / 有证据的异议 / 待澄清”。修复已获授权时，由实现角色优先处理阻碍项，再处理其他问题；每处补上直接检验预期行为的证据。复核者对更新后的版本再次检查该问题及受影响路径，并报告仍开放的问题、执行过的测试及其结果。

交付前核对：每条已确认发现均可复查；跳过的轴、缺失的证据和未完成的签核均已列出；复核对应最新提交或工作区状态；报告不含原始凭证。
