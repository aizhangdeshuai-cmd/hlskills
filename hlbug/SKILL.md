# Bug修复流程

> ## ⚠️ 能力边界声明
>
> 本技能"硬性关卡/强同步/会签"是**文档纪律**,靠 Agent 自觉 + 用户手动打断,**非** Claude Code runtime 强制(漏一步不自动阻断;Agent 模型弱或 prompt 冲突时关卡可能失效,需手动打断重读)。详见 `README.md` 「⚠️ 能力边界声明」。


## 通用纪律：完成前验证

## 交接段

> 本技能被 `hlchain` 编排为"全流程条件阶段 (任一阶段发现问题都触发)"。完成本技能后, Agent 应:
>
> 1. 验证 bug 修复已走完修复与验证全流程 (步骤 7-14, 含分支收尾与交付)
> 2. 询问用户: "bug 修复完成, 回到哪一阶段继续?"
> 3. 用户选择后, 调回原阶段对应的 Skill (如 hldev / hltest) 继续
>
> hlbug 是**横向**技能, 在 hlchain 任一阶段触发后, 修完回到原阶段, 不在主链路上。
>
> 如果用户是**单独调用本技能** (不在 hlchain 链路中), 此交接段不触发。

> **路径规范**：本文件涉及的 `docs/` 路径命名遵循 `hlpm/path-conventions.md` 中央规范（命名/深度/特例）。


**任何阶段标记"完成"前，必须识别并运行验证命令，读取输出并确认退出码通过。** 严禁"应该通过了"、"看起来正确"、"之前检查过了"、"可能没问题"等说法。证据先于断言，无一例外。未经新鲜验证证据，不得声称完成。

### 受阻停止纪律
- 任何步骤遇到阻塞，**立即停止**，不得猜测或强行绕过
- 3 次修复尝试失败 = 质疑架构方案，不尝试第 4 次变体修复

### 自调节机制
防止无限修复循环(以下为可执行判定规则,非概率计数):
- 单次修复涉及 > 3 个文件:**必须向用户说明范围溢出原因**,确认是否仍属本次 Bug 范畴
- 出现与本次 Bug 无关的文件变更:**立即回退该部分变更**,无关改动单独另开任务
- **硬上限:15 次修复尝试后停止**,汇总已试方案与结论向用户报告,不尝试第 16 次
- 修复引入新问题:回退本次修复,标记为"需人工介入"

### 调试纪律（融合 gstack /investigate）

**根因未确认前，禁止进入修复阶段。** 具体规则：
- 必须先完整收集证据（错误日志、堆栈、复现条件、环境信息），才能提出假设
- 每个假设必须可验证——"可能是 X 导致"不算验证，必须有具体验证步骤
- **症状 ≠ 根因**：console 报错是症状，为什么报错才是根因。修复症状不修复根因 = 埋下未来 Bug
- 对复杂 Bug 使用 `tracer` Agent 做因果追踪，对竞态条件、异步问题的排查优先级高于直觉判断
- 跨组件 Bug 先画调用链，再逐层排查

## 角色与 Agent 映射

| 角色 | Agent |
|------|-------|
| Bug分析+根因 | `debugger`(复杂场景调用 `tracer`) |
| 修复方案 | `debugger` + `architect` |
| 前端开发 | `executor` |
| 后端开发 | `executor`(`architect` 咨询) |
| 代码审查 | `code-reviewer` |
| 安全审查 | `security-reviewer` |
| 测试 | `qa-tester` |
| 验证 | `verifier` |

## Bug修复流程

### 第零阶段：加载项目上下文
0. **加载已有文档** — 修复之前先理解项目，避免孤立分析：
   - 如存在 `.hl/memory/` → Read 全部文件
   - 如存在技术设计文档 / API文档 / 数据库设计 → Read 加载相关模块
   - 如 Bug 涉及已分析过的模块 → 加载对应分析文档
   - **项目约束文件初始化**:检测项目根 AI 约束文件(Claude Code→`CLAUDE.md` / Codex→`AGENTS.md` / Cursor→`.cursor/rules/*.mdc`;检测不出或多 IDE 都写)。不存在 → 按 `hlkb/templates/claude-md.template.md` 创建;已存在 → 校验是否含 `## 🚨 完成前自检` 段,缺则追加该段(不重写其他)。详见 `hlkb` §项目约束文件。

### 第一阶段：问题定位
1. **Bug分析** — `debugger` 基于项目文档上下文理解Bug现象与影响范围。如用户提供Bug截图/录屏：优先用模型原生多模态识别，不支持则用 Read 工具读取图片；如需分析视频可使用可选外部 `videodb` 技能（需用户自行安装，未安装不影响本流程）
2. **根因定位** — `debugger` 主导根因分析(与其自述使命一致),`architect` 仅在根因涉及架构设计时咨询。遵循结构化调试四阶段（融合 gstack /investigate 方法论）：
   - **Investigation（证据收集）**：收集所有相关证据——错误日志、堆栈跟踪、复现条件、受影响范围
   - **Analysis（根因分析）**：从证据出发，追踪因果链路，定位根因而非症状
   - **Hypotheses（假设验证）**：对每个候选根因提出可验证假设，逐个排除
   - **铁律：根因未确认前，禁止进入修复阶段**。修复症状而不修复根因 = 隐藏未来 Bug
   - **复杂场景**：竞态/异步/跨组件 Bug 由 `debugger` 调用 `tracer` 做因果追踪（见调试纪律段）
3. **修复方案** — `debugger` + `architect` 制定修复方案(debugger 出根因修复点,architect 评估架构影响)
4. **用户确认方案** — 提交修复方案供用户确认

### 第二阶段：修复与验证
5. **Git 工作区准备** — 创建隔离工作区进行修复，避免污染主工作区
6. **修复开发** — `executor` 执行修复，遵循技术设计文档与编码标准
7. **修复自测** — 开发自测修复正确性，确保无回归
8. **代码审查** — `code-reviewer` 审查修复代码，确保无引入新问题
9. **安全审查** — `security-reviewer` 审查修复是否引入安全风险
10. **回归测试** — `qa-tester` 对受影响模块执行回归测试
11. **浏览器验证** — `qa-tester` 浏览器环境确认Bug已修复。非前端 Bug(纯后端/CLI/库)可跳过,在交付说明中标注"跳过浏览器验证及原因"
12. **分支完成** — 执行分支收尾,流程同 `hldev` 步骤 8(检测环境→验证测试→确定基础分支→4 选项:本地合并/推 PR/保持原样/丢弃→执行→清理),不在此重复定义
13. **最终验证** — `verifier` 验证修复完整性与安全性。如存在健康评分基线(`hltest`/health),修复后评分低于修复前基线 → 回退本次修复
14. **交付** — 更新相关文档，记录修复内容

## 变更传播规则

Bug修复涉及逻辑变更时，**受影响文档必须同步更新**：接口文档、数据库设计、测试用例、用户操作手册、帮助文档。确保代码逻辑与文档描述保持一致，不得出现文档与实现不符的情况。
