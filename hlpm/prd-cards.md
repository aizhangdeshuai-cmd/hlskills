# 步骤 4b · 标准 PRD

在所选版本目录生成 `prd.md`。新产品默认使用完整企业目录。已有项目增建独立模块可选模块目录，普通功能迭代使用[迭代 PRD（Mini）](prd-mini.md)。用户选定的形式和交付范围优先。

## 首页与覆盖范围

让首次评审的人先读懂一笔业务。用一段话说明谁遇到了什么问题、本期改变哪一步、哪个模块负责最终结果、谁从哪里看到变化。紧接本期范围、成功依据、需要本次评审决定的问题和功能索引。指标记录基线、目标和来源，暂缺基线时写取数方法及负责人。已有项目标明基线版本、受影响的 BL 和本次变化。演示假设显式标注。

使用[完整编号模板](templates/enterprise-prd.md)起稿。企业全目录从 `## 01 文档管理` 至 `## 17 附录` 保留每一个必备的 Markdown 标题、编号、父子层级和顺序。模块稿在标题下改用 `<!-- hlpm:module -->`，默认写 01～14、16、17，按原编号保留风险和附录。涉及本模块独立发布、迁移或回滚时填入完整第 15 章。跨节共用的规则只定义一次，其他小节写清适用结果及来源。

第 7 章保留 7.1.1–7.1.4，自 7.2 起每项功能单列十个编号小节。单功能第 11、12 项按需追加。第 16 章用约定的三栏表。企业全目录稿在文档标题下一行保留以下声明，供正式交接复核。

```markdown
# {产品名称} 产品需求文档 v{版本}
<!-- hlpm:enterprise -->

## 01 文档管理
```

| 02 | 产品概述 | 背景、现状与具体痛点、目标用户、产品定位、建设目标、核心价值及建设原则。新产品说明愿景，已有产品引用定位和目标基线。本期目标说明如何观察改进。 |
| 03 | 业务需求分析 | 描述业务背景、参与角色、使用场景和需求。定义业务对象、归属、彼此关系、状态和生命周期。核心规则给判断条件与处理结果，列业务约束与异常，引用相应 BL/BR/EX。 |
| 04 | 产品范围 | 列本期建设范围、非本期范围、优先级依据、版本规划和外部依赖。功能清单使用「功能编号、功能名称、功能说明、优先级、版本」，由 7.1 引用。延期项只写已决定的安排。 |
| 05 | 产品整体架构 | 附功能架构图，说明模块划分、层级、模块依赖、系统边界、上下游和数据流向，明确谁提供、谁处理、谁对最终结果负责。提供实际用户入口、导航和菜单路径。 |
| 06 | 业务流程设计 | 从一笔业务说明总体、核心及子流程。写前后置条件、跨模块交接、并行与汇合条件、状态流转、异常和终止或恢复去向。多个角色用泳道或等价分步文字标明谁接下一步。 |
| 07 | 功能需求详细设计 | 以 `### 7.1 功能模块总览` 列 7.1.1 模块说明、7.1.2 功能清单（引第 04 章）、7.1.3 功能依赖关系、7.1.4 功能优先级。自 7.2 起每个 BL 按下文单功能模板展开。 |
| 08 | 数据需求设计 | 说明数据总体架构、实体、ER 图、字典、类型与约束、主外键与关联、来源与归属、生命周期、完整性和一致性、导入导出、历史兼容及迁移。产品侧定义单位、精度、范围和旧数据解释口径，物理模型等按已确认的技术设计引用。 |
| 09 | 接口需求设计 | 说明总体约定、内部模块和外部系统、提供方与消费方、触发和交换内容。已有契约按版本引用 API、请求与响应、格式、认证授权、异常、超时、重试、幂等和接口版本管理。成功、重复及失败给出可观察的业务结果。 |
| 10 | 权限及安全设计 | 按用户角色列功能操作和数据访问矩阵，给出允许与拒绝路径、项目及组织范围、身份认证、操作日志与审计、敏感数据保护和查看权限。 |
| 11 | 非功能性需求 | 说明适用的性能、并发、稳定性、扩展性、可维护性、系统与浏览器及操作系统兼容性、易用性、数据安全、可观测性及日志。写明负载、测量方式、目标值或现行 SLO 的版本和条款。 |
| 12 | UI/UX 交互规范 | 统一布局、导航菜单、表单、按钮、弹窗、列表与表格。约定默认、空、加载等待、成功、出错、权限变化等页面状态与反馈，注明撤销及恢复、键盘焦点与跳转。页面和组件索引定位第 07 章具体控件及同版演示入口。 |
| 13 | 异常及边界场景 | 按业务筛查空数据、重复、非法、关联失效、多用户并发、网络中断、权限变化、数据冲突、系统故障及恢复。按「场景、受影响对象/状态、EX、BL、AC」索引到单功能预期，写清跨功能的影响与恢复。 |
| 14 | 测试及验收标准 | 给出测试范围、策略、代表性数据，覆盖适用的功能、业务流程、数据、接口、权限、异常、性能及回归。写明验收条件、阻断项和测试通过条件，以本页给出的 BL、AC、验证方式表形成追踪矩阵。AC 正文在各 BL，完整交接时链接真实用例及执行入口。 |
| 15 | 发布及上线要求 | 写发布计划、范围、版本、部署环境、配置、迁移与对账、上线检查、发布验证、回滚和上线后监控。提供可判定的放行与回滚条件、责任方、已办理业务如何保全及恢复后如何核对。具体命令、脚本、部署步骤和执行证据引用相应技术或发布交付物。 |
| 16 | 风险及待确认事项 | 仅保留「未确认需求」「外部依赖」「后续优化事项」三栏。分别写决定人及期限和受阻 BL/AC、依赖对象及所需交付与时间、已决定延期的范围。已知的业务、技术和数据风险写入适用的规则、异常、验收或上线条件，仍待决定的条目归入这三栏。 |
| 17 | 附录 | 提供术语与缩略语、参考资料及标准、相关图纸，按需索引业务流程图、功能架构图、数据模型图、数据字典、页面原型及实图。保留已有附录 A–H 的引用方式。 |

各类需求的写作重点见[按需求规模裁剪](SKILL.md#按需求规模裁剪)。标准稿中的每个必备小节都要保留。可在本节使用下列标注，表格里的事项在同一单元格内写全。英文标记 N/A、TBD 也可使用。

- `不适用。原因：本期全部额度从人事台账读取，员工和主管均无导入导出入口。`
- `待确认。事项：年末冻结如何核销。负责人：HR 政策负责人。确认节点：年度结算规则评审时、开发排期前。`

内置企业全目录每次生成后对实际文件运行 `python3 "$HLPM_DIR/handoff_trace.py" "$VERSION_DIR/prd.md" --enterprise`，模块稿使用 `--module`。按输出中的文件、编号和缺项修订，复验通过后用实际业务数据核对功能结果。

**第 08、09 章分别确认分工。** 已有约定时沿用。分工未定时，在首次需求提问中让用户为每章选产品侧写、开发侧写或本期不涉及。产品侧写业务定义并引用已确认的技术契约。开发侧写时，本章注明承接方和待补契约，关联 BL 仍写明可验收的业务结果。例：假期池的数据字典由产品规定半天为 0.5 天及历史单据单位，接口契约由开发补充，产品 AC 规定同一审批重复回执仅扣一次。未确定的端点、物理类型和阈值记录责任人。

## 功能卡片

按[第 7 章单功能模板](prd-feature.md)生成真正的 Markdown 标题与表格。每个 BL 一张卡，章序与功能编号各自维护，例如 `### 7.2 BL-1 新建项目分类`。十项均有适用内容或具体 N/A 理由。需要展示影响或延期边界时加第 11、12 项。仅交 PRD 时「可追溯测试」可写本卡可执行场景，完整交接时填实际 TC。

逐卡按[五条编写规范](prd-checks.md)评审。

固定全目录稿会核对第 7 章各定义表的必填列，以及字段（FLD）、规则（BR）、校验（VAL）、异常（EX）和验收条件（AC）的编号引用。共用定义直接引用原编号。引用项目既有字典时，在附录用「引用编号、来源及版本」两列表注明实际文件、版本及条款，开发和测试可从卡片回查同一原件。评审时再用真实输入核对公式、交互、错误恢复及验收预期。

## 客户指定目录

客户采用固定 16 章时，把确认过的目录随本版 PRD 保存为 `customer-outline.md`。按原章名和顺序写 `## 01 文档管理` 等 16 个标题，已指定的小节逐级写成 `### 1.1 文档基本信息` 等编号标题。目录依据取自客户原件，起稿前确定。客户只规定章名时，章内功能卡按实际业务展开。

选版时运行 `version.py prd-form existing --delivery prd --outline "$VERSION_DIR/customer-outline.md"`，在 PRD 首页标题下使用返回的 `<!-- hlpm:outline=customer-outline.md -->`。交付前运行 `python3 "$HLPM_DIR/handoff_trace.py" "$VERSION_DIR/prd.md" --outline "$VERSION_DIR/customer-outline.md"`。检查按客户目录核对标题、编号和正文，并复核第 7 章功能卡、第 14 章 BL/AC 验收索引及第 16 章三栏事项。下游按同一份声明复验。

**兼容既有交付。** 客户固定 16 章时保留客户目录，第 7 章容纳功能卡，第 14 章索引 AC，第 12、13、15 章按客户原目录放异常、UI 与上线内容。维护已有 15 字段卡时保留原 `§N BL-N` 标题、字段号及下游锚点，新要求补入原位。编号/名称/优先级/频率归基本信息，角色、前置、触发、主场景及扩展归入口和交互，业务逻辑及 §N.9.5 归字段、控件、规则、校验、异常与数据，§N.12 验收表承载 AC。保留 §N.10 决策、§N.11 埋点、§N.14 非功能、§N.15 未解决问题到相关章节的引用。每个 AC 在所属 BL 的表格首列定义一次。[功能卡实例与验收表](prd-feature.md)

**核对业务闭环。** 用代表性数据走通主路径与失败恢复。额度或库存取恰好耗尽的值再批准、结算或释放，核对各项余量。涉及代办或分属不同账户的数据，用同角色的甲乙分别核对明细和汇总。遇到到期未办、跨账期、状态被另一人改变，写清操作权限、刷新和结果归属。区分确无记录、读取失败、恢复读取，以及使用缓存的时间与可办范围。工业设计软件可取孔距 25.4 mm 的样件，按项目约定走英寸导入、编辑、导出、重新打开并实测，分开说明显示位数和几何容差。

## 截图的回填与复用

4b 记录计划演示的页面和状态。交付原型时用真实控件名称、角色、样例数据、操作、反馈和复位方式串成“试一遍”，链接同版 HTML 及已生成的需求标注或执行步骤。6b.5 取得实图后在评审前回填卡片与附录 D，完整交接复用同一页面、版本和状态的证据。链接相对本版 `prd.md`，如 `design/components/screenshot-card.png`。截图在范围内但渲染失败时注明“未取证”、原因和补验动作；用户豁免时记决定及范围。均保留可用 HTML 入口。纯后端以实际参数、原值/新值、单位、生效/回退条件及验证入口说明。
