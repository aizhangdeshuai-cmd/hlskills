# 产品需求与交付

## 启动与选版

一般产品需求默认走到测试用例评审（`workflow`）。用户明确只要分析、PRD（`prd`）或原型（`prototype`）时，停在约定阶段。明确只要 PRD 和用例时，从 PRD 评审直接进入测试阶段。正式交给开发实施才选 `handoff`。接续已有 PRD 或原型，先核实本版依据、交付范围和已完成的节点，从第一个未完成的节点继续。

## 需求澄清

1. 和用户走一笔真实业务。说明谁在什么入口遇到什么问题、本期要改变什么、怎样算办成。核对范围、规则优先级、权限、数据前后值、异常与恢复。已有答复或生效规则能确定的事项记录来源。把余下疑问集中列出，每项说明不同答案会改变的结果，等用户答复。收到部分答案只跟进余项。全部本期疑问获确认或被用户明确移出本期后才开始制作。制作中遇到新歧义也回到这里。催稿、免审或登记负责人都不能替代业务决定。
2. **业务确认后**，查当前工作空间是否有对应项目，定位实际页面、组件、样式、调用方或服务入口。告知找到的基线或已查范围。询问有无参考竞品、参考哪些操作或视觉细节。用户已答的直接沿用。有现有 UI 时确认沿用或替换的范围，有冲突只问差异点。有竞品时按[竞品 UI 取证](competitor-ui.md)区分所见行为和本期采纳项。涉及市场选型时按[市场调研](../hlresearch/SKILL.md)核实依据。若只涉及服务且无可演示界面，跟用户确认跳过原型。已有明确范围决定可直接记录。

## 按需求规模裁剪

3. 根据变更影响给出**本次文件清单、PRD 写法和理由**，询问是否增减。已选定或委托代选的直接沿用。采用分册时分别询问 08 数据和 09 接口要产品现在写、交开发写、产品阶段不生成，还是本期不涉及。只问仍需决定的项。微小变更用一页（`micro`），普通迭代用 Mini（`iteration`），新增跨模块能力、新产品或系统重构再展开标准稿（`module/product/rebuild`）。按实际影响判断，已有产品默认迭代。用户指定的写法、单文件或客户编号目录优先。

令 `HLPM_DIR` 为本技能目录。按实际项目状态、规模和终点选指引，例如 `python3 "$HLPM_DIR/version.py" prd-form existing --scale iteration --delivery workflow`。只读返回的 `guide`。`ask` 时确认影响交付的差异。客户固定目录用 `--outline`，显式选形式用 `--form`。按[版本约定](path-conventions.md#零版本目录与状态)用 `version.py list/resolve/new` 取得实际 `VERSION_DIR`，新稿默认在业务项目的 `knowledge/doc/vN/`。已有可续写版本先核对目标。已接收、完成或归档的产品变更另建版本。

## 需求与 PRD

4. 竞品、现有基线和清单确定后，**此时写齐 PRD 及已选产品文档**，包括选定的数据、接口、竞品或非功能说明。已选正式交接的，此时按[验收计划](handoff-package.md#验收计划)冻结确认来源。首页写目标、范围、交付安排和依据。每个功能（BL）写真实入口、条件、动作、状态或数值变化、失败后的去向，以及可观察的业务验收点（AC）。按已确认规则独立复算关键数值，检查每项变更至少有一条能检出漏做的验收。固定目录保留编号，确实不适用写原因。已移出本期的待确认事项给负责人和确认节点。[正文与附件分工、复算和去重](prd-checks.md)

新版标准/Mini 使用选版返回的声明，附录 08、09 链接已生成的同版分册或注明安排。14 此时只写 `测试阶段生成`。明确只要单文件简稿时，选版加 `--single --delivery prd`，声明用 `<!-- hlpm:single -->`，在正文附「验收索引」表 `BL | AC | 验证方式`。运行 `python3 "$HLPM_DIR/handoff_trace.py" "$VERSION_DIR/prd.md" --stage prd`，新稿按选定声明显式加 `--split`、`--split-mini` 或 `--single`。修复缺项再复验。客户固定目录按[客户目录约定](prd-cards.md#客户指定目录)处理。正文只链接当前实际可打开的材料。

## 角色与评审记录

**每次交付到下列节点，单独询问用户是否评审，可选全部、指定角色或跳过，等待当前节点的决定。** 已明确指示某一节点怎么做时直接执行。用户只选“评审”时使用该行全部角色。给出本版入口、检查结果和仍待验证的边界。

| 当前产物 | 可选评审方 | 通过或用户跳过后（已到约定终点即交付） |
|---|---|---|
| PRD 与已选产品文档（4.5） | 开发、测试、UI | 告知开始制作高保真原型。已确认跳过原型则告知开始编写测试用例。 |
| 可操作高保真原型（6b.6） | 产品、开发、测试 | 告知开始生成测试及验收标准和详细用例。 |
| 测试及验收标准和用例（8.5） | 产品、开发、UI | 交付本版文件和评审结论。已约定正式交接的继续打包。 |

每次评审记录实际参与者、版本、结论和证据。一次会话的多个视角如实标明。若有修改，按[同版同步规则](disciplines/strong-sync.md)修订所有受影响的已生成材料并复验，列出变动，再询问“要复审，还是确认这版并继续？”，等待答复。免审记录用户决定。自动检查通过不能代替评审。三轮仍有分歧交用户裁决。需要委派时查[角色分工](disciplines/role-boundary.md)。

## 设计阶段

6. 从评审通过或用户明确免审的本版 AC 和页面基线制作[可操作高保真原型](design-stage.md)。实际操作主流程和影响结果的分支，逐条核对交互反馈、同一对象的数据前后值和异常恢复。原型运行记录与候选环境待验项分别标明，回填同版演示入口、复演步骤和证据，再进入原型评审。约定 1:1 开发时，经确认的页面、状态、视口和允许差异按[还原交接](prototype-handoff.md)保留。

## 验收用例与交付

8. 根据本版 PRD、已确认的评审修改和适用原型编写 `acceptance-criteria.md`（范围、通过条件、BL/AC 验证索引）与 `test-cases.md`（TC、关联 AC、前置、输入与操作、可观察预期）。覆盖适用的正常、异常、边界、权限、恢复、回归及跨角色同一对象。更新 PRD 的真实 TC、附录和两份文件的引用。运行 `python3 "$HLPM_DIR/handoff_trace.py" "$VERSION_DIR/prd.md" --stage test --cases "$VERSION_DIR/test-cases.md"`，逐个核对业务预期，再询问用例评审。客户固定目录在原第 14 章填写标准和索引。由单文件简稿追加测试交付时，转为 Mini 分册，保留原 BL/AC 并补齐附录安排。

仅 `handoff` 追加[正式交接](handoff-package.md#完整交接步骤)。复用确认来源、编号及证据，补齐计划、矩阵和自检，按[基线约定](disciplines/baseline-commit.md)交接。返修先读同包拒收单，重走 9.5、11、12。用户选定进入开发后由 [hldev](../hldev/SKILL.md) 复验。
