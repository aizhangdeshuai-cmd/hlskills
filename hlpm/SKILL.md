# 多角色协作 · 产品段

## 启动与选版

**0. 明确本次交付。** 从用户原话和已选编排范围判断终点。只说要梳理或写一个需求时，先交 PRD。用户已说清目标就直接采用，只有不同理解会实质改变交付时才合并询问。

| 用户要拿到什么 | 交付范围 | 交到哪里 |
|---|---|---|
| “把半天假规则写成 PRD”“先给开发看一下这份需求” | `prd` | 4.5，交 PRD 和其中可验证的业务结果。涉及 UI 仍写明控件和反馈。 |
| “做个能点的原型”“给我演示员工申请、主管审批” | `prototype` | 6b.6，交 PRD 或已有需求依据、可打开的原型、操作方法与实际验证结果。 |
| “把需求交给开发和测试实施”“准备正式交接包”，或已选编排接下来进入开发 | `handoff` | 12.5，交通过完整检查的版本包、范围、摘要与复盘。 |

仅交当前阶段时按表中终点收口。后台规则需演示时，先确认可操作入口。

**0.5. 选形式与分工。** 以需求所属产品为准：已有业务页面、运行行为、生效 PRD 或用户明确是现有产品取 `existing`（默认迭代）；从零建设取 `new`（默认标准）；只有脚手架或依据矛盾取 `unknown`。用户指定形式或目录优先。令 `HLPM_DIR` 为本技能真实目录，运行：

```sh
python3 "$HLPM_DIR/version.py" prd-form existing --delivery prd
```

按下表传 `--scale`。用户指定形式用 `--form standard` 或 `--form iteration`（兼容 `mini`）。按返回的 `guide` 只读[标准](prd-cards.md)或[迭代](prd-mini.md)指引，`chapters` 给出所选写法的覆盖章号，`ask` 表示需确认。按 `stop_after` 交付。

告知所选形式、终点及依据。复用已给的约束和分工。UI 范围会影响本次交付且不清楚时询问。适用的数据需求设计、接口需求设计分别确认“产品侧写 / 开发侧写 / 本次不涉及”。两项可以混选，用户委托代选时技术详设优先交开发。产品负责业务口径和验收结果。未答复的分工留待确认，先处理已明确的需求。逐份说明本次涉及的评审时机。

**0.6. 定位版本和基线。** 按宿主读取项目约束；接续任务可从 `.hl/memory/working.md` 找上次进度，按路径、标题或 BL/AC 只读相关依据。涉及完整交接且需要补项目级自检约定时，沿用 [hlkb](../hlkb/SKILL.md) 的去重规则。先使用已有的 PRD、原型或用户指定的交付位置。需要版本目录时运行 `python3 "$HLPM_DIR/version.py" list "$PROJECT"`，已选版本用 `resolve "$PROJECT" <版本或目录>`，新建用 `new "$PROJECT"`；将实际路径记作 `VERSION_DIR`。

同号版本以实际目录消歧。已有 ready 或 rejected 版本且未指明目标时，告知续写或新建的选择。ready 只表示尚无开发状态标记，正式接收另验交接包。accepted、completed 或 archived 后发生产品变更时另建版本。返修先读同包拒收单，交开发复验时重走 9.5、11、12。轻量交付升级为正式包时沿用可续写的版本、来源和编号，复核其间的变化，再补正式交接的缺项。

## 按需求规模裁剪

根据需求中的页面、模块边界和发布范围判定规模，告知选择依据。用户指定的规模或目录优先。只有信息不足且两种选法会改变交付内容时，再请用户选择。标准稿从[完整编号模板](templates/enterprise-prd.md)取所选章节，保留各级原编号。迭代稿可在七项变更说明中合并相应主题。客户指定 16 章目录时，在选版命令追加 `--outline "$VERSION_DIR/customer-outline.md"`，使用返回的文首声明。见[客户目录](prd-cards.md#客户指定目录)。

| 需求规模 | 默认写法 | 重点章节 |
|---|---|---|
| 微小迭代 `micro` | 一页说明一个局部行为变更 | 01、02、04、07、14 |
| 普通功能迭代 `iteration` | Mini PRD 写旧行为、新行为和回归影响 | 01、02、03、04、07、14、16 |
| 新功能模块 `module` | 模块 PRD 写清模块边界及与现有产品的依赖 | 01～14、16、17。涉及独立上线、数据迁移或回滚时补第 15 章 |
| 新产品建设 `product` | 企业标准 PRD | 全部 17 章 |
| 核心系统重构 `rebuild` | 企业标准 PRD，关联开发承接的专项技术设计 | 全部 17 章，明确专项的负责人、范围与确认节点 |

## 角色与评审记录

按[角色加载方式](../SKILL.md#agent-使用方式)取本阶段用到的角色。`analyst` 起草需求，主代理或调用方写入，`designer` 负责版本内原型；正式交接时 `test-engineer` 编写业务用例，`verifier` 只读复核。[角色边界](disciplines/role-boundary.md)

在本次会产出的 PRD（4.5）、原型（6b.6）、正式用例（8.5）完成时按用户选择评审或免审。记录版本、实际参与者、结论与证据。待审、用户免审、已确认分别记录。需要评审时，从需求、架构、设计、实现与测试视角核对，保留或反对意见给出条件、证据与验证方法。同一会话采用多个视角须注明实际方式。

驳回后修订受影响的文档，按[强同步约定](disciplines/strong-sync.md)处理关联项。三轮仍有分歧请用户裁决。各阶段依据[验证纪律](disciplines/completion-validation.md)核查实际产物；正式交接按[基线约定](disciplines/baseline-commit.md)登记。

## 需求与 PRD

**1–3.5. 从场景确定范围。** 用一笔业务说明谁遇到什么问题、期望得到什么结果和哪些事项需决定。确认原话拆为可独立验收的约束，保留来源。术语或政策有多种合理解释时，说明各自改变谁的数据、哪步操作或结果，再集中确认。新产品明确用户和定位，有关键架构选择时比较 2–3 个可行方案及依据。用户指定竞品还原时再读[竞品 UI 取证](competitor-ui.md)，需要市场调研时读 [hlresearch](../hlresearch/SKILL.md)。样例可按明示假设演示。

仅 PRD 时把原话和验收场景写在正文。原型需要机器复跑时为相应场景准备计划。正式交接从本阶段起按[验收计划](handoff-package.md#验收计划)冻结已确认来源，并登记适用的跨角色、确认原型或竞品约束。

**4a–4b. 编写。** 首页记录本次范围、版本、形式与两项分工。确认功能点（BL）划分及优先级，明确本期新增、继承与边界。迭代复用已有编号、说明旧行为到新行为的变化；跨模块大改展开数据流、兼容和回归。已授权演示的假设标为 `[Assumption]`。使用版本目录时正文为 `prd.md`。

在所属 BL 下把每条确认约束关联到验收条件（AC）或已确认豁免。写出主路径及适用的拒绝、失败、重试、结果待核等分支，具体到对象、状态、数值或副作用。已有测试用例（TC）沿用编号；仅 PRD 时可直接写该条件如何验。UI 用真实控件名说明入口、操作和反馈，只链接实际存在的原型和证据。沿用的非功能指标给出处，缺基线时给测量方式与负责人。“待确认事项及风险”仅列未确认需求、外部依赖、后续优化事项，无项写“无”。

**4.5. 生成后自动检查。** 每次写入或修订内置企业标准 PRD 后运行 `python3 "$HLPM_DIR/handoff_trace.py" "$VERSION_DIR/prd.md" --enterprise`，指定其他交付路径时用实际文件。模块稿将 `--enterprise` 换为 `--module`，客户目录换为 `--outline "$VERSION_DIR/customer-outline.md"`，迭代稿省略格式参数。检查逐级编号、正文、豁免原因、未决项负责人和确认节点、功能卡及验收索引。按定位修订后复验。原型及正式交接从 PRD 文首读取所选目录。

**评审与交付。** 按[五条编写规范](prd-checks.md)从操作推演到数据和验收结果。迭代稿兼验原行为。对受时间、额度或归属影响的功能换一组输入再推演。终点为 4.5 时交出正文、检查结果、业务评审状态及影响决定的未决项。

## 设计阶段

**6a.0–6b.6. 制作和验证原型。** 原型及含 UI 的正式交接按[设计与验证](design-stage.md)从本版 PRD 提取每条验收条件。制作前确定入口、样例和会改变结果的分支。生成后实际操作，逐条核对交互反馈、数据前后值和异常恢复，运行覆盖检查。将同版入口、复演方法、实测结果和待验项回填 PRD。约定 1:1 还原时按[确认原型交接](prototype-handoff.md)保留视口、状态、证据和允许差异。原型交付止于 6b.6。无 UI 的完整交接直接进入步骤 8。

## 验收用例与交付

**8–12.5. 完整交接。** 仅当终点为 12.5 时读取[完整交接步骤](handoff-package.md#完整交接步骤)，编写并评审正式用例，核对一致性矩阵和非功能要求，验明适用原型及截图，自检、打包并复盘。按原件复核来源和正文摘要，阻断项在接收前解决。

## 交接段

完整包传递版本目录、适用范围、预期页面、评审情况、计划与正文摘要和仍需跟进的事项。已确认 UI 附还原依据，返修附同包证据。按[开发与测试接收范围](handoff-package.md#开发与测试的接收范围)区分上线行为和演示操作。由 hlchain 编排时返回本阶段结果，用户选定进入开发后交 [hldev](../hldev/SKILL.md) 复验。
