## 三条不可违反的边界

### 1. 产品段绝不修改产品代码

- 生产工程中的源代码由 `hldev` 负责。
- 产品段产出需求与验收文档。涉及 UI 时，版本设计包内可包含可操作 HTML 及其样式、脚本、脱敏样例和验证资源。
- 即使 PRD 写"该字段校验函数改为 XXX" —— 产品段只描述**业务行为**,**不写实现代码**

### 2. 代码修改唯一入口是 `hldev`

- 即便只是"改一行字段名" / "加一个状态判断" / "修一个正则",也必须由 `hldev` 接手
- 产品段可以**在 PRD 里描述需求**,但**代码层面动手**必须交开发段

### 3. 设计稿是条件性输出,不是必出

- 本期交原型，或完整交接涉及 UI、交互、页面布局及视觉变化时，提供可操作的设计稿。仅交 PRD 时将界面行为和验收写在文内。
- 纯后端 / 数据结构 / 接口 / 状态机 / 业务规则 / 算法变化 → **不出设计稿**
- 步骤 6a.0 沿用启动时确认的 UI 范围，只有范围仍不清楚时再询问。

## 输出范围总览

仅交 PRD 时在 4.5 核对需求与文内验收场景。交 PRD 与原型时，在 6b.6 核对交互实物及其实际验证结果。需要交接到开发或测试时，执行[完整交接清单](../handoff-package.md)。

## 角色与 Agent 映射

| 角色 | Agent | 用途 |
|------|-------|------|
| 产品经理 | `analyst` / `planner` | analyst 起草 PRD、分析需求与主持评审，planner 提供规划意见 |
| UI/UX 设计师 | `designer` | 界面设计、设计评审主持 |
| 前端开发 | `executor` | UI 可实现性评审、前端组件复用评估 |
| 后端开发 | `architect` / `executor` | 技术可行性、数据流转评审 |
| 代码审查 | `code-reviewer` | (开发段使用) |
| 测试 | `test-engineer` / `qa-tester` | 用例编写与评审、E2E 场景 |
| 验证 | `verifier` | 一致性矩阵验证、交付物自检 |
| 用户(我) | — | 关键节点确认者 |

---

## Agent 能力边界(重要)

> - `analyst` 是**只读 Agent** (`disallowedTools: Write, Edit`), 仅负责**分析 / 评审 / 内容生成**(以消息形式输出)
> - 版本 PRD、一致性矩阵和交付自检由主代理或负责写入的调用方保存。`planner` 提供规划意见及版本内依据，返回内容给调用方。
> - `designer` 写版本设计包，`test-engineer` 写本期业务验收用例。参与可行性或设计评审时，`executor` 返回评审意见。生产实现交给开发阶段。
> - 步骤说明中"X Agent 编写" = "X Agent 生成内容 + 主 agent 或调用方写入文件"
> - `verifier` 只读，按产品阶段的证据出具通过、失败或待验证的判定。

## 启动检查清单(第 0 阶段必读)

启动产品段前,确认以下 5 件事:
- [ ] 确认本技能是"产品段",**不是开发段**; 代码修改请启动 `hldev`
- [ ] 确认本次交到 PRD、原型还是完整交接，以及约定范围内的 UI 变化
- [ ] 按当前产品入口确认阶段与适用条件，记录跳过设计、截图或调研的原因
- [ ] 确认项目已有 `.hl/memory/` 和 `knowledge/`(老项目兼容 `docs/`)的现状
- [ ] **理解兜底铁律**:需求分析(步骤 1)中,凡没理解/不确定/模棱两可的,必须问用户到无任何问题,并复述确认

## 交付后同步知识库

完整交接的步骤 12 将本期 BL、AC 和 TC 及其版本路径同步到 `knowledge/prd.md` 和 `knowledge/tests/`。沿用既有编号，补交同一修订时更新对应条目。尚待开发的实现标为待实现。步骤 12.5 在 `knowledge/retro/` 记录产品段复盘。各类条目的归属见 [hlkb](../../hlkb/SKILL.md)。
