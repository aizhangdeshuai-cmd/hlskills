# 三项一致性检查规则与矩阵模板

> 属于 `hlpm` 技能第 9.5 步骤。
> 核心目的：确保 PRD / 设计稿 / 测试用例三项交付物逻辑完全一致。
> 开发段（`hldev`）以此为验证基准。全篇的设计列、设计版本和设计复审仅在涉及设计时适用；纯后端迭代填 N/A，核对 PRD、用例和矩阵版本。

---

## 强同步规则（v5 核心）

**触发条件**：任一项因评审驳回而回退修改。

**强同步行为**：
1. 在所选交付目录修改源项，修订号 +1
2. 检查另外两项是否需要同步修改
3. 同步修改受影响的项，版本号 +1
4. 按原评审选择重评该份及已产生且受牵连的文档，见下表
5. 评审通过后，重新生成一致性矩阵
6. 登记适用文档共同对应的修订基线，列出沿用的文档版本。修订同一包时保留目录名。

**触发示例**：

| 评审模式 | 触发源 | 必须同步 | 必须重走评审 |
|---------|-------|---------|------------|
| 逐份立即评审(v22 起唯一评审机制) | PRD 立即评审(4.5)驳回 | 设计 + 用例(若已产出且牵连) | 只重评 PRD(4.5);牵连带重评对应立即评审(6b.6/8.5) |
| 逐份立即评审(v22 起唯一评审机制) | 设计立即评审(6b.6)驳回 | PRD(如影响业务逻辑) + 用例 | PRD 重评(4.5,若改) + 设计重评(6b.6) + 用例重评(8.5,若牵连) |
| 逐份立即评审(v22 起唯一评审机制) | 用例立即评审(8.5)驳回 | PRD(反查) + 设计(反查) | 对应文档重评(4.5/6b.6,若改) + 用例重评(8.5) |

> 注:v22 前的"分阶段评审(旧选项 B,步骤 5/7/9)"与"集中评审(旧选项 C,9c)"已取消,仅为历史模式,仅供追溯,不再作为可触发行。

**3 轮回退上限**：单项评审最多驳回 3 轮，超出升级用户决策。

**填写规则（3 个子表通用）**：
- 每条适用非功能指标填写验收方法和依据。涉及 UI 才写视觉实现策略，后端填写接口或任务层的可观察结果。
- **设计实现策略 = UI 层的体现方式**（如"骨架屏 / 虚拟滚动 / 错误脱敏 / 浏览器前缀"），**不写架构策略**（如"负载均衡 / 缓存层"——这些是技术设计文档范畴）
- 性能目标注明来源、负载及适用范围。沿用既有 SLO 时列出处；缺基线写测量方法、负责人及待测状态。
- 安全需含具体策略（不能只写"安全"二字）
- 兼容性按实际宿主、接口或设备核对。范围外项目标 N/A 并说明理由。
- 约定的压测、安全或兼容性检查缺失时保留证据缺口。

**逐项判断适用性。** 始终评估安全影响，写出本期受影响的控制或继续适用的既有策略。超出本期范围的检查记 N/A 并附依据。性能与兼容项如经确认延期，在不一致清单登记影响、负责人和补测条件。已约定的安全控制或其他放行要求缺证据时保留阻断。

### 5. 代码实现追踪矩阵(4 维防御基础）

**目的**：在产品段交付物基础上，**开发段用于追踪每条 PRD 规则的代码实现状态**。这是 4 维防御（漏实现 / 错误实现 / 非功能漏实现 / 范围越界）的统一追踪表。

按[开发与测试的接收范围](handoff-package.md#开发与测试的接收范围)，每个已确认交付的 AC 预建一行，保留编号与关联 TC，供开发回填实现证据和候选结果。

| AC | PRD 条款及实现位置 | 设计页面 | 关联 TC | 实现提交 SHA | 候选 SHA 与验证证据 | 实现状态 | 偏离说明 |
|---|---|---|---|---|---|---|---|
| <AC 编号> | <BL、条款及位置> | | <TC 编号> | | | 待开发 | |

**实现状态枚举**（开发验收时填写，产品阶段初始为待开发）：

| 状态 | 含义 | 触发动作 |
|------|------|---------|
| ✅ 已实现 | 代码完全符合 PRD 规则 | 无 |
| ❌ 未实现 | PRD 有规则但代码未实现（场景 A） | 步骤 4.5 标记 + 步骤 7.5 走查不通过 |
| ⚠️ 偏离 | 代码实现了但语义不一致（场景 B/C） | 步骤 4.5 标记 + 步骤 7.5 走查 + 触发强同步 |
| ➕ 越界 | 代码实现了 PRD 未定义的功能（场景 D） | 通知产品段确认：保留则补 PRD / 移除则删代码 |
| N/A | 不适用（如仅设计相关） | 标灰跳过 |

**填写规则**：
- 实现位置及 SHA 以修改该规则行为的实际补丁为据，可用 git log -p 定位。登记候选提交、运行记录和结果；复用既有实现时沿用原提交并重新验证候选
- 偏离说明必填：必须含 PRD 条款引用 + 实际实现描述
- 每完成一个业务规则 / 状态机分支 / 非功能实现 → 立即更新（步骤 4.5）
- 走查阶段（步骤 7.5）核对当前候选提交的每个适用项和实际测试证据。N/A 需说明原因，待验证或有阻断时保留未通过状态

**与 v5 一致性矩阵的关系**：
- v5 矩阵（1-4）：产品段用，**PRD ↔ 设计 ↔ 用例**三方覆盖
- v10 矩阵（5）：开发段用，**PRD ↔ 代码**四方追踪
- 两个矩阵都以本期确认范围为分母。产品交接检查 AC 与 TC 的双向关联，开发验收核实实现位置及同一候选的执行结果

**按风险确定证据深度。** 本期每条适用规则都需关联代码提交、可观察的验收条件及运行证据。小改可把这些引用合写一行。涉及退款权限和退款状态时，两条规则分别验收，按开发段核心模块要求保留人工复核。仅对实际不适用的项记录 N/A 及原因。

**与开发段拒收分类的对应关系**（P2-11 评审补充）：
- ✅ 已实现 ↔ handoff-rejection.md §9 无偏离项
- ❌ 未实现 ↔ **A 漏实现**（场景 A）
- ⚠️ 偏离（语义）↔ **B 错误实现**（场景 B）
- ⚠️ 偏离（非功能）↔ **C 非功能/安全漏实现**（场景 C）
- ➕ 越界 ↔ **D 范围越界**（场景 D）
- N/A ↔ 不适用，无需对应

## 提取方法（如何填充矩阵）

### 从 PRD 提取

1. 从所属 BL 的规则、边界及异常提取业务规则，按 AC 关联 TC。迭代版从行为差异及应保留的基线行为取同样的信息。
2. 从状态机总图或 BL 内的前后状态提取本期相关实体的状态与转移。
3. 从权限矩阵或 BL 内的角色约束提取谁可对哪些数据执行什么操作，保留依据的位置。

### 从设计稿提取

1. 每个 HTML 页面 = 1 个设计页面
2. 参照 [hldesign](../hldesign/SKILL.md) 的 5 态检查适用状态，与 PRD 定义的业务状态分别核对。
3. 权限控制点：登录拦截、按钮可见性、页面访问限制 = 权限点

### 从测试用例提取

1. 每个 TC = 1 个测试用例
2. 用 TC 的前置条件核对 PRD 的角色、数据及起始状态，原型准备这些条件的操作留在演示步骤。
3. TC 的"预期结果"应与 PRD 验收条件一致

### 交叉比对

对每个矩阵：
- 从 BL 和 AC 追到 TC、适用设计页面与证据；开发验收再追到 UT/IT 或人工验证记录。遇到悬空编号标记缺口。
- 任一缺失 = ❌
- 存在但内容不符 = ⚠️

## 一致性矩阵的演进

**每次重走评审后**：
- 修改源项 → 更新对应行
- 同步项 → 同步更新对应行
- 重新提取 → 更新版本号
- 重新走 9.5 步骤 → 输出新一致性矩阵

**版本一致性**：
- 一致性矩阵的版本号 = 当前三项版本号（vX）
- 强同步触发时，一致性矩阵版本号同步 +1

## 常见不一致模式（避免清单）

| 模式 | 表现 | 防范 |
|------|------|------|
| 业务规则遗漏 | PRD 写了规则但无测试用例 | 用例评审时强制反查 PRD |
| 状态机缺态 | PRD 定义 5 态但设计只画 3 态 | 设计评审时强制比对状态机 |
| 权限漏测 | 设计有权限控制但无反向测试 | 用例评审时强制要求正反向 |
| 字段不一致 | PRD 字段名 ≠ 设计字段名 ≠ 用例字段名 | 三方使用统一的字段术语表 |
| 交互流程偏差 | PRD 主流程 A → B → C，但设计稿显示 A → C | 设计评审时按 PRD 流程逐页核对 |
| 验收条件模糊 | PRD 验收"性能良好"，但无具体指标 | 记录目标来源或现有 SLO；缺少目标时记录待确认责任人及日期 |
