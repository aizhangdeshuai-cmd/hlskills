# 8 项产品交付物打包模板（产品段 → 开发段）

> 完整交接时按本模板打包 8 项交付物（5 必出、3 条件出）到所选版本目录（新版本默认在 `knowledge/doc/vN/`）。承接先前的 PRD 或原型时，复用同版已确认内容和可复核的实测证据，再补齐本次交接范围。`version.py list` 的 `ready` 只表示版本尚无开发状态标记，正式交接依据是本版完整检查及其计划、正文摘要。

## 交付清单（8 项，5 必出 + 3 条件出）

以下相对路径均以同一个选定的版本目录为根（含旧项目的 `docs/vN/`）。

| # | 交付物 | 路径模板 | 必出/条件 | 负责 Agent |
|---|--------|---------|-----------|-----------|
| 1 | 竞品分析报告 | `analysis/competitive-analysis.md` | 条件（本期有品类调研或方案选型） | `analyst` 核证，主代理形成建议并写入 |
| 2 | PRD 文档 | `prd.md` | **必出** | `analyst` 生成 → 写入文件 |
| 3 | 设计稿 | `design/ 下的页面及 components/、flows/ 中的 HTML` | 条件(涉及 UI) | `designer` |

| 5 | 验收计划与测试用例 | `acceptance-plan.json`、`acceptance-sources.sha256`、`test-cases.md` | **必出** | 主代理保留确认来源，`test-engineer` 编制用例 |

## 验收计划

各自能独立验收的必测条件优先拆成独立 TC。同一 TC 共用多个必测参数、测试层或分片时，由产品与测试在确认计划中登记 [`required_variants` 及报告映射](../hltest/acceptance-reports.md#必测变体)，候选验收按同一计划检查各项到齐。

在步骤 1 填写 `scope` 与 `sources`，按原始消息、工单或合同逐项记录已确认约束。每个 `origin` 指向可复核的位置，`text` 保留原意。从用户原件确认完整后运行以下命令登记来源指纹，将指纹与确认记录一同保留。在后续步骤填 `acs`、`scenarios` 时指纹保持有效。源要求真有变化时记录新决定、旧基线和影响，经确认再带 `--renew` 更新。指纹可发现后续误删或改写，原话完整性和决定权仍需回查原件。

```sh
python3 "$HLPM_DIR/acceptance_plan.py" freeze-sources "$VERSION_DIR/acceptance-plan.json"
```

首次冻结生成 `hlpm-v3` 来源指纹，签出时核对 PRD 验收点、用例与关键断言。涉及 UI 的 v2、v3 包逐 AC 检查 `design/interaction-check.md`，失败、未测或缺表均阻断。旧纯摘要包沿用原 TC 检查，已有逐 AC 表仍参与核对。旧包运行 `--renew` 重新确认后进入 v3。

### 开发与测试的接收范围

正式计划中的 AC 和 TC 只描述本次已确认要交付的产品行为。展示效果时，评审稿可按 PRD 首页明示的假设演示。交接引用 PRD「未确认需求」中影响实现或验收的条目、受影响的 BL/AC 和确认人，决定后再交接受影响的范围。外部依赖按对本期验收的实际影响处理，后续优化留待相应版本。

数据需求设计和接口需求设计按用户选择分别交接。产品侧写的项引用 PRD 或已确认契约的版本、位置与对应 BL/AC。开发侧写的项凭已确认的业务依据接收，例如哪笔数据归谁、何时生效、重复或失败后应观察到什么结果，技术定义进入开发步骤 3。本期无关的项按已定范围跳过。旧包沿用已确认的定义，归属影响本次工作时再核实。

TC 的前置条件写成可复现的业务状态，如“以主管身份查看一笔待审批申请”。原型可用模拟身份、固定日期或重置样例布置现场，候选用测试账号与数据准备相同条件。专为演示的控件和复位自测写在原型说明或 `design/interaction-check.md`。产品明确要求上线身份切换或数据重置时，按真实角色、数据范围和副作用另写业务 AC。

接手旧包时，若 AC 或 TC 把演示操作列为正式预期，由产品核对原始要求，保留业务编号和断言，将演示步骤归回前置或原型自测。同步计划、用例、矩阵、受影响的证据及交接摘要后复验。曾列入正式范围的条款，调整时记录原编号与决定依据。

以下示例是一条最终可交付的跨页面场景。每个 TC 代表独立可重复的验收场景；同一 AC 可有多个 TC。已有测试或浏览器流程可沿用其测试实现。纯 API、CLI 或服务规则的 `pages` 为 `[]`。用 `scope` 固定项目、功能与本期修订。

```json
{
  "scope": "开票项目/作废/v1-r1",
  "sources": [{"id":"REQ-01","origin":"需求单 INV-17 第3条","text":"确认作废后，同一发票在列表和详情中都显示已作废","acs":["AC-01"]}],
  "scenarios": [{"id":"TC-01","acs":["AC-01"],"pages":["list.html","detail.html"],"object":"INV-001"}]
}
```

被明确决定移出本期的来源仍保留原话，写 `"acs":[], "waiver":{"reason":"范围或延期原因","origin":"确认人及决定位置"}`。本期纳入的 AC 均须有 TC。按已确认要求拆分角色与资源归属、允许/拒绝、状态边、失败恢复及副作用。写操作需能核对操作号、最终结果和相应写入次数；跨两个及以上不同页面时，按操作顺序写 `pages`，例如列表打开详情再返回列表可写 `["list.html","detail.html","list.html"]`。同一业务对象填稳定的脱敏 `object` 并逐页断言标识和结果。从列表打开全局帮助等无业务实体的导航填 `"no_object_reason":"帮助入口适用于所有发票"`；由产品回核该原因是否符合场景。

涉及设备或断点的要求，在原始来源中保留其依据。按受影响任务选取视口，把 CSS 像素宽高写在对应 TC 的 `"viewport":[1024,768]`。有浏览器竞品契约时只填其已有的 `reference.recipe` 中的 `viewport`。同一业务动作需要在两个视口独立验收时分配两个 TC，共用 AC。用例表的“输入与操作”和“预期结果”写到用户任务结束，例如“在订单菜单点击导出 → 页面显示本次导出完成”。设计、开发和 QA 按 TC 取同一份条件。

正式交接检查读取以下 Markdown 定义表。保留列名及首列，其余列可追加。多个 AC 或 TC 以逗号或空格分隔。表格采用 Markdown 表头、分隔行和数据行。正文引用、围栏内示例都不算定义。

| 文件 | 定义表必需列 |
|---|---|
| `prd.md` | 两种形式均在所属 BL 标题下定义一次 `AC / 验收点 / 可追溯测试`。如 `## BL-1 名称`、功能章节内的 `### BL-1 名称`，或沿用 `## §1 BL-1 名称`。全局验收汇总引用编号。 |
| `test-cases.md` | `TC / 关联 AC / 前置条件 / 输入与操作 / 预期结果`。每条写出能区分正确与错误实现的预期。 |
| `consistency-matrix.md` §1 | `AC / 所属 BL 及规则位置 / 设计页面或 N/A 原因 / 关联 TC / 验收方法`。页面填相对 design/ 的路径，多页以逗号分隔；无 UI 写 `N/A` 及理由。 |
| `consistency-matrix.md` §5 | `AC / 关联 TC / 实现状态`。预填本期每个 AC 和场景。开发字段见[实现追踪矩阵](consistency-rules.md)。 |

有 UI 时按[设计验证](design-stage.md)在实际页面执行场景，随包提交 `design/interaction-check.md` 和关联的运行证据。检查器核对来源、双向编号、BL 归属、适用页面和交互证据。角色、业务语义、断言强度及设计观感由内容评审复核。

### 把关键业务预期连到断言

首次打包前，把数额、状态、权限等写错会改变验收结论的预期登记在计划顶层的 `case_assertions`，在 PRD 所属 AC 的「验收点」与该 TC 的「预期结果」格中，用同一个链接把实际期望值嵌进原句。不同人、不同处理时点的结果分别指到相应断言，保留对象及前后条件。

- **已有原型回放。** 例如 `"case_assertions":{"TC-01":{"steps":["L19","L20-L22"]}}`。若 `TC-01.steps` 第 19 行检查订单待审批，20–22 行依次检查可用、冻结、已用，表内写 `状态「[待审批](design/checks/TC-01.steps#L19)」，余额（可用 / 冻结 / 已用）[7 / 2 / 3](design/checks/TC-01.steps#L20-L22)`。按用例叙述顺序登记本 TC 的断言行，可引用单行或一段连续断言。文本和对象断言取其预期值，控制状态断言分别显示「隐藏」「禁用」「启用」。步骤调整时同步位置并重跑；交接仍校验该配方和原型文件的实跑摘要。
- **API、CLI 或其他可复用的业务值。** 例如 `"case_assertions":{"TC-02":{"values":{"writes":0}}}`。表内写 `拒绝后新增 [0](acceptance-plan.json#/case_assertions/TC-02/values/writes) 笔记录`。字段名采用字母、数字、下划线或短横线，值使用单行文本、整数或布尔值；小数精度有业务意义时用文本。候选测试直接读取 `plan["case_assertions"]["TC-02"]["values"]["writes"]` 作预期，另从被测服务读取真实写入次数。产品检查确认表与预期一致，候选阶段再验证实际行为。

每条登记的预期在本 TC 出现一次，并由至少一条关联 AC 引用。例如批准后余额写成「周宁原单已批准，余额 `[0 / 0 / 8](design/checks/TC-07.steps#L17-L19)`」。v3 会阻断错值、漏链与跨用例错挂。旧版按原登记范围核对。评审人对照原需求核实哪些业务结果需要登记，以及链接的对象、步骤和时机。

同一角色跨页或回访时，可在 TC 的 `visits` 按 `pages` 顺序逐次登记 `expect`（控件到业务预期文字）。在每次原型访问用 `expect-visible-text` 核对，候选用同一组预期验收。纯 UI 对照或能同时核完业务的浏览器回放，在冻结计划时分别登记 `visual_only` 或逐 AC 的 `business_checkpoints`。[候选记录格式与示例](../hltest/acceptance-reports.md#同角色跨页和回访)

### 跨角色验收

需求原话若承诺“一方办理后，另一方能查到同一对象的结果”，将这条独立来源标记为 `"cross_role": true` 后登记来源指纹。它关联的每个 AC 都要有标准 `scenarios` 里的跨角色 TC。业务方确定角色、真实入口、单号、同步时机，以及每一方应见的值。单角色页面继续使用既有步骤。

例如员工提交后主管批准，员工再查同一单。以下是一条 TC 的完整定义。每个角色的 `identity` 为身份控件与可见文字，`visits` 与 `pages` 一一对应。每次访问都用 `object_at` 核对单号，再用 `expect` 核对业务结果。

```json
{
  "id": "TC-08", "acs": ["AC-02"], "object": "L-004",
  "pages": ["employee.html", "manager.html", "employee.html"],
  "roles": {
    "employee": {"entry":"employee.html","identity":["#actor","林沐"]},
    "manager":  {"entry":"manager.html","identity":["#actor","陈岚"]}
  },
  "visits": [
    {"role":"employee","object_at":"#request-id","expect":{"#status":"待审批","#frozen":"2"}},
    {"role":"manager","object_at":"#request-id","expect":{"#status":"已通过"}},
    {"role":"employee","object_at":"#request-id","expect":{"#status":"已通过","#frozen":"0"}}
  ]
}
```

在该 TC 的 `.steps` 中按办理次序写 `role employee`、真实提交操作、`checkpoint`，再写 `role manager`、批准操作、`checkpoint`，最后 `role employee`、`checkpoint`。约定刷新可见时先写 `reload`，约定自动同步时直接检查。原型工具在同一离线浏览器上下文为不同角色打开独立页签，检查时逐端读取身份、单号和实际值。按本包原有命令执行及交接，缺一次回访或结果有误都会定位到对应 TC。正式候选由 QA 在各自登录会话采集[同一 TC 的逐端实测](../hltest/acceptance-reports.md#跨角色候选记录)。

### 确认原型的开发依据

要求按已确认的原型还原前端时，在对应来源登记 `prototype_ui: true`，给该范围的 TC 绑定 `prototype_match`。交给开发同一份可操作样本、确认依据、样式资源和复验契约。字段、采集命令和候选复验见[从确认原型还原前端](prototype-handoff.md)。

### 竞品交互证据

仅在本期明确要求还原给定竞品 UI 时，为对应的 `sources` 条目标记 `"reference_ui": true`，在澄清阶段随来源执行 `freeze-sources`。每个纳入范围的 AC 至少关联一个带 `reference` 的 UI 场景。独立可漏验的行为分配不同 TC；已有市场调研按原交付条件处理。`--competitive` 决定是否提交市场报告。操作观察与项目适配见[竞品 UI 对照](competitor-ui.md)。

以下字段加到原有 TC 中。相对路径从版本目录起算。参考产品、页面、角色、视口或视频时间点等定位信息按材料写入 `origin` 或所指的观察记录。定稿时对已审阅的参考文件运行 `shasum -a 256 <文件>`，将其摘要填入 `sha256`。原型和开发候选沿用该基线。

```json
"reference": {
  "mode": "browser",
  "origin": "订单演示站 v2 的订单列表，测试店员，桌面 1280×720，筛选菜单",
  "recipe": "analysis/reference/menu-tc01.json",
  "baseline": "analysis/reference/TC-01/observation.json",
  "sha256": "<已审阅基线文件的 64 位 SHA-256>",
  "adaptation": "按产品决定 UI-7 沿用本项目品牌色，仅跟随菜单位置与关闭行为"
}
```

- **可操作网页。** `mode=browser` 时，用本库 `hlbrowse/reference_check.py` 按同一份操作与测量规则先 `capture` 竞品，再 `compare` `design/` 内 TC 起始页。比较结果写入 `design/checks/<TC>.reference/observation.json`，保留同目录截图与基线所附证据。交接会重核规则、参考摘要、场景、起始页及实测的本地资源。经确认的差异写进可选字段 `adaptation`，并在规则中选择实际要跟随的维度。开发、QA 接收相同规则和基线，在实际候选版本再执行比较。
- **截图、录屏或人工实测。** `mode=manual` 时填写 `origin`、`baseline`、`sha256`、`kind`（`screenshot`、`recording`、`observation`）及 `dimension`（`appearance`、`interaction`、`motion`）。截图仅支撑该帧的外观；操作与动效须有可核对的录像区间或真实操作记录。评审人对照参考与当前原型，在 `design/checks/<TC>.reference/observation.json` 登记 `scenario`、`reviewer`、`when`、`expected`、`actual`、`status`，并填写 `baseline_sha256` 与 `prototype_sha256`。后者是**本次原型运行报告** `design/checks/<TC>.json` 的原始文件摘要；`status=pass` 才能通过。候选另按 [QA 报告格式](../hltest/acceptance-reports.md) 实测。
  使用截图或录屏原件时，把实际原型同状态的截图或短录像保存在本次人工报告所在目录或子目录。记录 `"actual_artifact":"frames/menu-open.png"` 和 `actual_sha256`（该文件的原始字节摘要）。原件使用 `baseline` 单独留存。外观截图可用 PNG、JPEG、WebP；动效的两侧材料都须含多帧，以本机 `ffprobe` 核对可读视频帧，签核人复核变化内容和时间点。录屏优先用 MP4 或 WebM，无法解码的动画可导出短录像。普通截图无需视频工具。
- **未观察到。** `mode=pending` 填 `origin` 和 `reason`，保留待证项直至补到材料。必测项仍待证时正式交接失败。产品明确决定移出本期时，使用来源清单已有的 `waiver` 记录决定与依据。

### 文件检查

产品打包、`hlchain` 阶段交接和 `hldev` 接收时都运行本目录的 `check-handoff.py`。三个参数分别取自产品段已经确定的设计范围、步骤 6b.5 截图条件和竞品调研条件。在自检报告记录实际版本目录、三个开关及原因。涉及 UI 时把所有预期 HTML 的相对路径逐一作为 `--page` 参数传入（如 `--page components/cart.html --page orders.html`）。下游复用同一份参数与页面清单，避免只验证碰巧存在的文件。以既有系统纯后端迭代、无需截图或竞品调研为例：

```bash
python3 "/实际技能目录/hlpm/check-handoff.py" "$VERSION_DIR" --ui no --screenshots no --competitive no
```

运行前将 `VERSION_DIR` 设为步骤 0.6 返回的实际目录。产品交接人在定稿后将两项输出保存在交接记录并传给开发与 QA。`plan_sha256` 对应 `acceptance-plan.json` 的原始字节。`spec_sha256` 同时绑定 `prd.md`、`test-cases.md`、`non-functional-requirements.md` 的文件名与原始字节。开发可以继续在矩阵回填提交和验证结果。

开发接收时从上游交接记录取得 `HANDOFF_SPEC_SHA256`，沿用本包相同的三个开关及预期页面清单，在上述命令末尾追加 `--spec-sha256 "$HANDOFF_SPEC_SHA256"`，并将输出的 `plan_sha256` 与上游记录比对。QA 使用同一对摘要复验。定稿文档发生变更时，先复核差异与受影响的用例，取得新交接记录后再接收。旧包可加 `--files-only` 盘点原有文件。正式接收前从已确认原件补录计划并按表头整理现有定义，再运行正式检查。通过后核对页面内容、截图状态、各文档实际修订及签核。

## 版本号管理

记录已选版本的实际路径。评审驳回或需求调整后，按[强同步规则](disciplines/strong-sync.md)同步受影响的文档及修订号，保留上一次拒收和修复证据。产品、开发和编排使用同一个交付目录。产品段复盘在产品交付后记录，开发段复盘由开发验收后补写。

## 自检清单

逐项填写下表，作为 `handoff-self-check.md`。使用“待核、通过、失败、不适用”；通过须能回查检查结果，不适用须说明原因。每次按实际修订更新结果，未执行的检查保留待核。

| 检查对象 | 验证方法 |
|---|---|
| 1. PRD | 标准版沿目标和业务流程核对适用功能卡。迭代版从基线复核旧行为、新行为、影响与回归项。按本版分工核对适用的数据与接口业务依据、可观察的 AC、TC 及 UI 入口。记录角色抽问的实际问题和证据。 |
| 2. 设计 | 涉及 UI 时按本期页面清单检查设计规范、钉点、适用状态、不同视口和无障碍证据。交互状态以 [hldesign](../hldesign/SKILL.md) 为准。模板控件自测和业务 AC 分别记录。纯后端整栏填“不适用＋原因”。 |
| 3. 测试用例 | 每个 TC 指向对应 AC，写出前置条件、输入、预期结果；覆盖主要路径、异常、边界和适用权限。缺少 UI 的功能使用接口、CLI 或集成验证。 |
| 4. 验收条件 | 核对矩阵 §1 的 BL、AC、TC 编号及验收方法。抽查同一 AC 的不同分支能否追到独立用例。 |
| 5. 非功能 | 按影响填写性能、安全和兼容性。沿用指标时引用现有 SLO 及适用版本；缺基线写测量方法、负责人和待测项。不适用说明范围。会影响放行的待测项保留为阻碍。 |
| 6. 一致性矩阵 | 对照业务规则、状态机、权限、非功能和不一致清单。适用设计列关联实际页面；无 UI 时标注原因。核对版本以及被牵连的文档；未关闭项记录负责人和下一次复核。 |
| 6.5 代码实现追踪 | 产品段给矩阵 §5 建立规则行及稳定编号，实现标为待开发。开发段再填写实际提交 SHA、代码测试、结果与偏离说明。 |
| 7. 版本一致性 | 记录 PRD、用例、矩阵及适用设计的实际版本，检查同一目录、同一次修订。 |

## 完整交接步骤

**8. 验收用例。** `test-engineer` 将用例写入 `{version_dir}/test-cases.md`。有界面时结合本版本 PRD 与设计；后端需求结合 PRD 与接口、参数及数据约束。覆盖实际的主路径、替代与异常、边界、权限及端到端场景。在验收计划补全所有场景，在用例表用相同 TC 记录前置条件、输入与操作、预期结果和关联 AC；适用的 UI 用例在编号前引用 6b.5 保存的实际页面或状态截图。[把关键业务预期连到断言](#把关键业务预期连到断言)，由 QA 复核所选业务字段与办理时机。沿用已有编号，代码层 UT/IT 由开发补写。登记基线版本。

**8.5. 用例评审。** 按 AC 核对可执行的 TC。若承诺另一角色看到结果，指出对方仍显示旧状态时哪个 TC 会失败，按[跨角色验收](#跨角色验收)登记。评审发现缺口时回到 4b 或 6b 同步修订；用户免审时记录决定，进入一致性终检。

**9.5. 一致性终检。** `analyst` 按[一致性矩阵](consistency-rules.md)抽取业务规则、状态机、权限及非功能要求，主代理写入 `{version_dir}/consistency-matrix.md`，只读 `verifier` 核对。逐个核验 BL → AC → 一个或多个 TC，设计适用时按本期页面清单逐项核对页面实物和状态。纯后端的设计列填写 N/A 和原因。设计托管在子目录时使用完整相对路径。为性能、安全、兼容保留来源、适用场景、负责人和验证方法；既有指标可引用，“待测”保留为缺口，影响验收时需明确处理。

检查矩阵的数据行和不一致清单。产品段保留代码测试、提交及实现结果待开发回填；适用的产品项能逐行追溯、豁免有据、阻断缺口已处理后才能通过。发生不一致时回到 4b、6b 或 8，更新受影响的 BL/AC/TC、流程、页面和证据。同版未变内容引用现有记录。需评审的文档重评；对于此前免审、此次因一致性问题修订的文档，告知影响并记录用户是否补评。

**10. 非功能需求。** 将适用的性能、安全、兼容性指标与验证方式写入 `{version_dir}/non-functional-requirements.md`，与矩阵对齐。使用现有 SLO 或接口兼容策略时写出文件、版本和章节。以实际需求决定是否需要 QPS、延迟或浏览器清单。

**11、12. 自检与打包。** 依据[自检清单](#自检清单)完成内容自检并写入 `{version_dir}/handoff-self-check.md`。一共五项必交（PRD、用例、非功能、矩阵、自检），三项按条件交（竞品、设计、截图）。逐份填写真实版本、状态、审查范围和证据。按所选目录及本期 UI、截图、竞品范围运行交接检查器，传入步骤 6 的预期页面。交接时传递成功输出的 `plan_sha256`、`spec_sha256` 与版本目录，对照来源原件复核语义。将本版 PRD 和验收用例按稳定 ID 归入 `knowledge/prd.md`、`knowledge/tests/`，补交时更新对应版本和条目。本版被选为当前交接包时，在需求索引单独一行维护所选 PRD 的链接，如 `[当前交接包](doc/v2/prd.md)`；旧包使用 `../docs/v2/prd.md`。明确切换时更新该行，历史版本保留普通链接。

**12.5. 复盘。** 产品包自检并打包后，用 `python3 "$HLPM_DIR/version.py" retro "$PROJECT" "$VERSION_DIR"` 取得实际包的 `package` 和 `report`，按[复盘约定](path-conventions.md#022-包身份与复盘)写入产品段的驳回及原因、表述实质缺口与误报、假设核对、矩阵不一致类别、大纲修订及本期踩坑。交接时附上包路径和复盘路径。可复现的坑按 [hlkb](../hlkb/SKILL.md) 记入 `knowledge/pitfalls/`。
