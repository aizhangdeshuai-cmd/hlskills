# hlpm 使用说明

> **多角色协作的产品段(从需求到交付物)**
> 完整规范见 [`SKILL.md`](./SKILL.md),本 README 聚焦"怎么用"

---

## 这是什么

`hlpm` 是 hlskills 体系中**多角色协作(产品+开发)流程的"产品段"**。
当你的团队是"产品经理 + 开发"两个角色分工时,用这个技能。

**它做什么**:接收你的需求 → 输出 8 类交付物(5 必出 + 3 条件出) → 交给 `hldev` 开发
**它不做什么**:不改任何代码(改代码请用 `hldev`)

---

## 什么时候用

✅ **适合用 hlpm**:
- 你负责产品,开发同事负责代码
- 需求从你这里发起,需要先评审再交接
- 团队有"评审会签"机制

❌ **不适合**(改用其他技能):
- 你一个人跑全流程 → 用 `hl-flow`
- 你要直接改代码 → 用 `hldev`
- 你要复盘/重构已有项目 → 用 `hllegacy` / `hlrefactor`

│
├─ 我有产品+开发分工,需求从我这发起
│  │

│  │  └─ 👉 用 hlchain(6 阶段编排,自动调 hlpm/hldev/hlrelease/hldeploy)

## PRD 输出长啥样

按"**功能点剖切**(默认)"组织 — 每个 BL 自成一节,读完一节即获该功能全貌:

```
§0  上下文 + 业务背景 + Non-Goals + 假设清单 + 章节地图
§1  BL-1 卡片(15 字段:用例编号/名称/优先级/角色/前置/触发/主功能/拓展/业务逻辑/决策/埋点/验证/频率/NFR/未决)
§2  BL-2 卡片
...
§12 BL-12 卡片
附录 A  状态机总图(跨功能 Mermaid)
附录 B  角色 × 权限点矩阵
附录 C  数据埋点全表
附录 D  原型截图引用
附录 E  关键决策点对比(如 BL-12 的 3 方案)
附录 F  v{N} 与 v{N-1} 差异清单
附录 G  业务流程总图(跨 BL 端到端,Mermaid + 文字双轨;PRD 仅 1 个 BL 或各 BL 相互独立无流程衔接时可豁免,需 4a 大纲显式标注)
```

**对照**: 旧式 PRD 按"业务逻辑/操作流程/数据流转/状态机/权限"5 大维度剖切 — 读一个功能点要跳 5 个章节。新式按"功能点"剖切 — 读 BL-12 一节搞定,横切内容(状态机全图/权限矩阵/业务流程总图)走附录。

详细 15 字段模板见 [`SKILL.md` §"PRD 编写"](./SKILL.md) 或 [`INTRO.md` §"PRD 章节结构"](./INTRO.md)。

> **关键判断点**: 你能独立完成开发吗?
> - **能** → hl-flow(单人 28 步)
> - **不能,需要开发同事** → hlpm + hldev(产品段 + 开发段分工)或 hlchain(全链路一次跑完)

## 5 步快速上手

### 第 1 步:启动技能

```
/hlpm
```

或自然语言:`我有个新需求,启动产品段流程`

启动后 AI 会自动执行**启动检查清单**(详见 SKILL.md 顶部):
- 确认是产品段(非开发段)
- 询问是否涉及设计
- 告知评审模式(逐份立即评审,v22 起唯一;v27 起不再提问)

### 第 2 步:回答 1 个问题(0.5 步)

| 问题 | 选项 | 影响 |
|------|------|------|
| **Q1 涉及设计** | 涉及 / 不涉及 | 决定是否出设计稿(不涉及 → 跳过整个第二阶段) |

> 评审模式不再提问(v27 起):逐份立即评审是唯一模式(v22 起),启动时 AI 会直接告知。每份文档产出后仍会问"需要/不需要评审"(4.5/6b.6/8.5)。

**不知道怎么答?**(v25 起不再选择需求规模,一律按复杂需求标准执行):
- 简单改动(如改 1 个按钮/字段) → 逐份立即评审下,三份产出都可选"不需要评审",全程零评审开销
- 常规需求 → 每份产出后选"需要评审",5 角色当场评

### 第 3 步:AI 帮你跑流程

AI 会**自动执行**以下步骤(你只需要在阻塞点回答问题):

```
加载项目上下文 → 选版本目录 → 需求分析 → 竞品分析(条件) →
PRD 编写 → 设计(条件) → 用例编写 → 逐份立即评审(4.5/6b.6/8.5) →
一致性终检 → 非功能需求(步骤 10) → 自检报告 → 打包交付
```

**关键节点**(AI 会主动停下来问你):
- 2a:有参考竞品吗?
- 0.6:有历史未开发版本,要在旧版本上改还是新建?
- 4.5/6b.6/8.5:逐份立即评审(每份文档产出后问"需要评审吗")
- 强同步触发时:哪几项要重走

### 第 4 步:查看产出物

完成后,所有交付物在 `docs/v{ver}/` 目录:

```
docs/v1/
├── prd.md                            ← PRD(必出)
├── test-cases.md                     ← 测试用例(必出)
├── non-functional-requirements.md    ← 非功能需求(必出)
├── consistency-matrix.md             ← 一致性矩阵(必出)
├── handoff-self-check.md             ← 自检报告(必出)
├── design/
│   └── *.html                        ← 设计稿(条件出)
└── analysis/
    └── competitive-analysis.md        ← 竞品分析(条件出)
```

`{ver}` 是 0.6 步自动决定的版本号(`v1` / `v2` / `v3` ...)。

### 第 5 步:通知开发接手

把 `docs/v{ver}/` 整个目录路径告诉开发同事(或直接说"启动 hldev")。

**开发接手会做**:
- 验证 14 项交付物齐全 (8 项产品段 + 6 项开发段补充)
- 验证版本号一致(PRD v1 = 设计 v1 = 用例 v1)
- 验证一致性矩阵全部 ✅
- 验证自检报告签字方完整
- **任一不合规 → 拒收 + 给你拒收原因**(详见 `hldev/handoff-rejection.md`)

## 关键概念

### 评审模式

| 模式 | 评审场次 | 适合 | 不通过时 |
|------|---------|------|---------|
| **逐份立即评审**(v22 起唯一) | 每份文档产出后当场 1 次(PRD 4.5 / 设计 6b.6 / 用例 8.5,各 5 角色) | 所有需求通用 | 驳回 → 当场改 → 只重评该份;牵连其他文档则连带重评 |

> 分阶段评审 / 集中评审:v22 起已取消,仅作历史注记(原步骤 5/7/9/9c 已 DEPRECATED)。

**逐份立即评审 ≠ "少评审"**: 仍是 5 角色 (`analyst` 主持 + `architect` + `designer` + `executor` + `test-engineer`), 只是从"攒到最后评"改为"每份产出当场评", 反馈更即时。简单需求可对每份选"不需要评审"直接通过,全程零评审开销。

**强同步规则**:任一评审驳回后,后续**相关评审必须重走**(逐份立即评审模式下,重评被牵连的对应份)。
- 例:设计评审(6b.6)被驳回 → 若改动牵连 PRD/用例,PRD 评审(4.5)+ 用例评审(8.5)也要重走

### 版本目录

每次产品段流程产出到独立目录 `docs/v{N}/`,不覆盖历史。

**启动时会自动**:
- 扫描历史版本(看 `.dev-completed` 标记文件)
- 如果有"未开发"的旧版本 → 问你"在旧版本上改 / 新建版本"
- 全部已开发 → 自动建新版本(如 `v3`)

**好处**:不会丢失历史;可对比各版本差异;开发拒收后产品可在原版本补齐。

### 设计规范遵循(硬性)

**如果你项目里有设计规范**(`docs/design/spec.md`):
- AI 会读取规范
- 设计稿必须**字面遵循**(颜色/字号/间距值都按规范,不可"参考发挥")
- 每条设计决策都要在 HTML/CSS 注释里引用规范条款(如 `/* 规范: §3.2 圆角值 */`)

**如果项目里没有规范**:
- AI 会输出"未发现设计规范"报告
- 你可以选择:先用 `hllegacy` 整理规范 / 直接开始设计

### 已有页面微调

**如果你要在已有页面上改**:
- AI 会先问"全新页面 / 已有页面微调"
- 选"已有页面微调" → AI 会读原页面代码 → 输出**3 区块 diff 设计稿**:
  - 区块 1: 原页面代码(diff 基线)
  - 区块 2: 改动清单(每条改动 + 原因 + 规范引用 + 影响范围)
  - 区块 3: 修改后完整页面(diff 标记)

文件名用 `.diff.html` 后缀(如 `order-list.diff.html`)。

## 常见问题

### Q1:为什么我不能直接改代码?

**A**:本技能是"产品段",职责是"定义做什么",不负责"怎么实现"。改代码是 `hldev` 的职责。这样分工的好处:
- 产品专注于业务规则
- 开发专注于实现质量
- 角色边界清晰,可拒收可追溯

即使只是"改一行字段名",也建议走 `hldev`,因为:
- dev 会跑测试,确保改动不破坏现有功能
- dev 会做代码审查
- dev 会在版本控制里留完整记录

### Q2:小需求也要走完整流程吗?

**A**:流程步骤是统一的(v25 起不再按需求规模裁剪,一律按复杂需求标准执行),但评审开销可控:
- 逐份立即评审下,简单改动可对每份产出选"不需要评审"直接通过,全程零评审开销
- 不涉及设计的需求 → 跳过整个第二阶段

### Q3:评审被驳回后会发生什么?

**A**:
- 单项评审驳回 → 返回对应步骤修改 → 重走该评审(最多 3 轮)
- 3 轮后仍不通过 → 升级到用户决策(让你判断)
- 触发强同步 → 后续已通过的评审也必须重走(防止"只改一处,其他地方不一致")

### Q4:如果开发拒收怎么办?

**A**:开发会填写 `handoff-rejection.md`(拒收单)给你,**说明拒收原因**(可能是缺文档/版本不一致/内部矛盾等)。

你需要:
1. 看拒收原因
2. 回到产品段补齐(可能回到步骤 4/6b/8/11)
3. 重走对应评审
4. 重新打包交付

**完整拒收流程**见 [`hldev/handoff-rejection.md`](../hldev/handoff-rejection.md)。

### Q5:可以同时跑多个需求吗?

**A**:可以,但**每个需求走独立版本目录**:
- 需求 A → 走 `docs/v1/`
- 需求 B → 走 `docs/v2/`
- 需求 C → 走 `docs/v3/`

需求之间互不干扰,可同时进行(AI 会按版本号区分)。

### Q6:设计规范在哪里维护?

**A**:项目级规范放在:
- 优先 `docs/design/spec.md`
- 备选 `docs/design/SKILL.md` / `docs/design/*.md`
- 兜底 项目根目录 `DESIGN.md`

如果没有规范,**先调用 `hllegacy` 第 11 步整理规范**,再启动产品段。

### Q7:我应该用 hlpm 还是 hl-flow?

| 场景 | 用哪个 |
|------|-------|
| 团队只有你一个人(产品+开发都你做) | `hl-flow` |
| 团队有产品+开发分工 | `hlpm` + `hldev` |
| 已有项目,要做小改动 | `hlpm` + `hldev`(逐份立即评审,简单改动可选"不需要评审") |
| 全新项目 0→1 | `hlpm` + `hldev` (产品段产 PRD/用例,再 hldev 接手) |

**`hl-flow` (单人跑全流程) / `hlpm` (产品段多角色) / `hldev` (开发段多角色) 三件套, 按需选用**。

## 实战示例

### 示例 1:加 1 个导出按钮(简单改动)

```
你: "我有个新需求:订单列表页加个'导出 CSV'按钮,触发下载当前筛选结果"
AI: [启动 hlpm]
    Q1 设计: A 涉及(加按钮是 UI 变化);评审模式固定逐份立即评审(v27 起不再问)
    4.5/6b.6/8.5: 简单改动,三份均选"不需要评审"
AI: [扫描历史版本,无 → 建 v1]
AI: [需求分析]
AI: [2a 无参考竞品 → 跳过竞品分析]
AI: [写 PRD,包含 1 条业务规则:点击导出按钮 → 下载 CSV]
AI: [4.5 PRD 立即评审:用户选"不需要评审" → 直接通过]
AI: [设计稿:基于原订单列表页 diff]
    区块 1: 原页面代码
    区块 2: 🟢 新增"导出 CSV"按钮(规范引用 §4.1 按钮 4 态)
    区块 3: 修改后页面(diff-add 标记)
AI: [6b.6 设计立即评审:用户选"不需要评审" → 直接通过]
AI: [写测试用例: TC-001 验证按钮存在 + 触发下载]

AI: [输出 8 类文档到 docs/v1/]
你: "启动 hldev"
开发: [接手,加按钮,跑测试,创 .dev-completed 标记]
```
