# 步骤 6a–6b.6 · 设计与验证

使用步骤 0.6 选定的实际版本目录 `{version_dir}`。标准 PRD 从第 12 章或附录 H.1 找到页面清单，再到第 7 章相应 BL 的第 4、5 项确认字段、控件和交互。客户目录沿用其 UI 章节，迭代稿从受影响 BL 的入口开始。按角色、页面、所属 BL 和本版 HTML 相对路径找到实际交付范围。

## 6a.0 确认范围

复用启动时选定的交付范围。仅交 PRD 的任务在 4.5 结束。若用户要看原型、现有描述却只有后端行为，先确认要演示的用户入口。纯后端的完整交接可直接进入[步骤 8](SKILL.md#验收用例与交付)。有 UI 时逐页确认全新、微调或沿用，列出本次实际要交付的页面、组件和流程。迭代只处理本版新增、修改及被牵连的部分，多个 BL 可以共用一个页面。

写页面前，从本版 PRD 的功能卡生成逐 AC 核对表。命令输出到终端，将表合入本版 `design/interaction-check.md`，保留已有操作记录和 TC 链接。外部需求没有验收编号时，按 4b 在本版 PRD 建立带原文出处的功能卡，复核编号和预期再取表。

```sh
python3 "$HLPM_DIR/prototype_checks.py" outline "$VERSION_DIR/prd.md"
```

读每条 AC 及其引用的规则、异常条款，按[原型检查项](prototype-checks.md)选出适用场景。同一 AC 中可以分别做错的分支要拆行，保留原编号，后续行的「PRD 验收点」可写「同上」。例如写入时断连，分别准备尚未写入、已写入却未收到回执两个起点。先填入口、角色、初态、输入和步骤。若完整交接已有 TC 计划，沿用其中的场景，再实现业务控件及可重演的异常触发与复位方式。

## 6a.1 核对规范

已有 hllegacy 交接时，沿实际条目回读已核实的规范和状态。其余情况按[设计规范查找顺序](path-conventions.md#42-设计规范文件查找优先级6a1-步骤)查找。记录实际路径、版本及适用章节。找到规范时列出字体、色彩、间距、圆角与阴影、组件状态、动效，逐项核对项目原有组件与参考页面。数值与取值以对应条款为准。

指定竞品还原时，从[任务与原件](competitor-ui.md)取得约定的场景、视口及项目保留项，先把可观察的差异落实到 PRD 控件表和 AC，再制作对应状态。

未发现规范时记录检查范围，询问是否通过 hllegacy 的设计规范整理流程补建，或采用哪一个现有页面作为依据。规范与需求冲突、已有规范未覆盖所需场景时，列出冲突条款和待决定的值，等决定后再制作受影响的页面。保存检查报告后进入 6a.2。

## 6a.2 设计稿格式

每页一份可离线打开的静态 HTML，带本地样式、脚本及 BL 钉点。布局、交互和示例内容接近上线形态。表单、按钮、筛选、分页、弹窗及 tab 按实际需求实现可操作的反馈；用本地模拟数据及明确的业务条件触发成功、校验失败、空、加载和错误等适用状态。需要请求的场景可以本地模拟其输入、响应和失败条件。浏览器中能使用 `?state=error` 等参数或抽屉的场景按钮复验。

业务交互脚本可内联。列表、详情、编辑、多弹窗或可独立审阅的复杂组件可拆成各自能打开的 HTML，并同步本期页面清单。各页复用本地样式及控制器，使用能在实际目录下解析的相对路径。普通 HTML 链接直接进入业务演示，同页加 `?bl-review=1` 可看需求标注。PRD 引用普通链接作为演示入口。

给演示者一个明确的起点和可重复使用的样例。例如从预约详情点击“改期”，选择新时段、确认，回到详情看到更新后的时间。用业务控件触发正常路径和适用的拒绝、错误恢复。复位方式写在卡片里，状态应持久化时保留刷新语义，复位仅恢复这份演示的数据。

## 6b 生成设计稿

以下路径相对于 `{version_dir}/design/`。

| 范围 | 交付路径 | 评审依据 |
|---|---|---|
| 全新页面 | `<page-name>.html` | 本期 BL 卡片、项目规范、现有组件或已确认参考页 |
| 已有页面微调 | `<page-name>.diff.html` | 原页面实现、原路径及对应基线 |
| 独立组件 | `components/<component-name>.html` | 组件行为、调用页面及关联 BL |
| 流程 | `flows/<flow-name>.html` | 本期业务流程、页面入口及参与角色 |

**全新页面。** 使用真实感示例数据。核对主流程、适用异常及操作者可见反馈。让开发能沿页面入口找到实际的布局容器、复用组件、设计变量和资源。复杂布局说明哪些区域固定、滚动或随视口重排，以及各状态用到的断点、动效或键盘行为。在页面或样式源注明项目规范出处，例如 `/* 规范: knowledge/design/spec.md §3.2 */`。工程交接引用 CSS、字体与图标原件，保留已确认的替代资源及原因。

**已有页面微调。** 找到原页面实现（如 `src/pages/` 或 `app/views/`）和历史版本的实际位置。需要上版设计时按步骤 0.6 解析其目录。原页面无法定位时先记录已查位置并向用户确认来源。保留原布局与交互，只改本次范围。成品含三个可对照的区块：

1. 原页面基线，含来源、版本和改动位置，使用 `data-diff-mode="baseline"`。
2. 变更清单 `data-diff-summary`，每项给选择器或控件、变更原因、规范引用、影响的 BL/AC 或 TC。
3. 修改后的完整页面 `data-diff-mode="modified"`。新增用 `<ins>` 或 `diff-add`，修改用 `<mark>` 或 `diff-mod`，删除用 `<del>` 或 `diff-del`。对照检查每个标记都能回到对应清单项。

演示和前端基线都打开修改后的业务页面。将评审专属说明或旧内容包在 `data-bl-review-only` 中，变更强调色和划线只在 `html[data-bl-mode="review"]` 下生效。用修改态的可访问名称或稳定选择器定位控件，避免旧页面出现同名控件导致选错。

### 接入 BL 钉点

从本技能的[模板 HTML](templates/bl-marker/bl-marker-template.html)、[样式](templates/bl-marker/bl-marker.css)和[控制器](templates/bl-marker/bl-marker.js)复制到设计包。模板提供抽屉及关闭、宽度调节和悬浮开关的完整 DOM 与事件处理。保留模板的元素 ID、可访问名称、键盘操作和脚本次序。新建页面须从模板替换示例内容和需求数据。资源副本按需编辑，技能原件可供其他版本复用。

1. 在每个对应控件附近放入 `<button type="button" class="bl-pin" data-bl="bl1" aria-label="查看 BL-1">1</button>`，父容器设置 `position: relative`。沿用模板 `<html data-bl-mode="demo">` 和头部的模式初始化。评审链接可点钉位或用悬浮开关切换显隐。业务页面使用对应的按钮、输入框、链接及可访问名称。
2. 按页面在其控制器副本内填写 `REQUIREMENTS`。每个键与本页 `data-bl` 相配。多页使用不同 BL 时，引用各自的数据副本，例如 `orders-bl-marker.js` 与 `cart-bl-marker.js`；相同数据才共用同一控制器副本。复制到子目录的页面相应调整资源路径。
3. 每个 BL 含 `title` 和 `sections[]`，按本版 PRD 摘录“一句话、主场景、替代/异常场景、业务规则、状态机变化、AC 验收表”。没有状态变化写明原因。主、替代和异常场景用 `[flow]` 开头，步骤用 `→` 或换行连接，`3a.`、`3b.` 表示分支。其余正文可用普通段落、编号列表、Markdown 表格。AC 引用对应编号与可观察结果。
4. 有异常态的章节写入 `state`（如 `error`）。用户点击“查看该状态”时，页面可监听 `bl:state` 并调用 `preventDefault()` 就地切态；没有自处理时核对 `?state=` 重载能够复原抽屉。悬停钉点能读到“一句话”首行。
5. 用 `?bl-test=1` 打开控件面板，核对抽屉和钉点双向对应。导航由 6b.5.1 在正常页面实测。记录面板的通过、失败和跳过。

登记设计基线及实际页面清单。更改已出基线的页面时同步更新受影响的 BL 引用。

## 6b.5 截图与回填

从本期页面清单的预期路径逐个打开实际 HTML。约定交付截图时，通过本库 [hlbrowse](../hlbrowse/SKILL.md) 为每页保存一张默认态 PNG，将明确用作 AC 或 TC 证据的关键异常态另存一张。

| 页面（相对 design/） | 默认图 | 异常态示例 |
|---|---|---|
| `orders.html` | `screenshot-orders.png` | `screenshot-orders-error.png` |
| `orders.diff.html` | `screenshot-orders.diff.png` | `screenshot-orders.diff-empty.png` |
| `components/card.html` | `components/screenshot-card.png` | `components/screenshot-card-error.png` |

默认图与 HTML 同目录，文件名保留完整的页面名（包含 `.diff`）。钉点显隐取与 AC 相符的状态。取得实图后将链接回填到 BL，使用截图索引时同步更新该索引，记录源 HTML、版本和状态；后续用例引用同一份证据。渲染失败记录页面、原因和补验动作，可写入 `{version_dir}/design/screenshot-errors.log`。约定必交的图缺失时记待补；明确豁免则在自检记录范围与原因。返工后只替换受影响的证据与引用。

完整交接会用 Pillow 解码每张必交 PNG。若约定某张图展示特定视口，在 `acceptance-plan.json` 顶层写 `"screenshot_viewports":{"screenshot-manager.png":"TC-02"}`，使用 `design/` 下的实际相对路径。按该 TC 的 CSS 视口以 1 倍像素比例截取当前屏（`screenshot --viewport screenshot-manager.png`），交接按图核对实际像素宽高。整页、局部或高像素比例的截图可按其拍摄方式留存，尺寸只对已声明的视口图检查。

## 6b.5.1 实测交互

从业务入口逐行操作，在同一张表分别填实际的控件与反馈、同一对象的前后状态或数值、故障时允许的动作及恢复结果。人工记录注明本版页面、角色和适用视口，机器执行沿用运行报告的被测资源版本或摘要。核对控制台异常。无关维度写「不适用：具体原因」。证据可链接已有 TC 运行记录、可复核的人工操作记录，或本报告内实测小节的锚点。独立 HTML 报告可按本版相对路径引用。链接到具体条目，或使用含 AC/关联 TC 的表格行；该条目中应能找到表内某项实际观察原文，也可在观察格用反引号摘录原始读数。记录封装在脚本或附件中时另附执行原件或可复核的人工记录。原型入口只用于定位操作。截图可证明所示画面，跨端同步、扣减次数与重试需有操作前后的观察。

生成或修订原型后，复跑受影响分支，交付前运行以下检查。

```sh
python3 "$HLPM_DIR/prototype_checks.py" check "$VERSION_DIR/prd.md" "$VERSION_DIR/design/interaction-check.md"
```

命令核对 AC 归属、PRD 预期、三项实测记录与证据引用。引用本库 `design/checks/TC-*.json` 的实测行会复核本版计划、所属 AC、执行状态、步骤和页面摘要。以其他名称引用且保留 `scenario`、`steps_sha256` 的本库记录也执行同一检查。其他工具的 JSON 按该工具的实际字段和原始记录由评审人核对。执行者比对观察值，评审人回到原文核实分支覆盖。原型可验的项未跑记「未测」，观察与 PRD 不符记「失败」，修正后按原条件复验。本地仅能模拟的项记「模拟通过」，写明真实环境的复验条件；只能在候选环境观察的项记「仅候选待验」。超出本次原型范围的项记「不适用」并说明原因。交付时分别汇总，附剩余问题与证据。

**完整交接或明确要求机器复跑时**，复用这张表的场景和证据，继续准备 TC。

按 `acceptance-plan.json` 里各 TC 的 `pages`（相对于 `design/`）准备可复跑的操作。普通场景从首项进入，跨角色场景从各自的[角色入口](handoff-package.md#跨角色验收)进入。原型工具读取[本场景的约定视口](handoff-package.md#验收计划)。用真实控件走到用例表的预期终态，例如导出用例要点击菜单内的导出项并断言成功反馈。依次列出必须验证的页面，返回列表或刷新后须再核对的页面可重复列入。涉及同一对象的联动时，在对应场景加 `"object":"I-001"` 等脱敏唯一标识，每次计划访问分别断言标识和该对象的状态。纯导航等无共享实体的跨页场景用 `no_object_reason` 说明。角色、成功、拒绝、失败、取消和刷新按对应 AC 分场景验。

例如列表中的发票 I-001 提交后需在详情保留待确认。将以下操作写入版本内 `design/checks/TC-01.steps`，选择器与值使用实际页面数据。

```text
expect-object "#invoice-I-001 .number" I-001
fill #reason 开具重复
click "#invoice-I-001 .submit"
expect-visible-text "#invoice-I-001 .status" 待确认
click "#invoice-I-001 .detail"
expect-object #invoice-number I-001
expect-visible-text #status 待确认
reload
expect-object #invoice-number I-001
expect-visible-text #status 待确认
```

在产品阶段从已确认的场景沿用稳定 TC 编号，步骤 8 编写用例时复用。运行 `python3 "$HLPM_DIR/prototype_evidence.py" run "$VERSION_DIR" TC-01`。命令在 Chromium 离线会话执行整条路径，验证实际页面上的钉点配置，输出 `design/checks/TC-01.json`。样式、脚本和测试数据随设计稿交付，使用脱敏样本。键盘、权限及隐藏态可用 `press`、`expect-disabled`、`expect-enabled`、`expect-hidden`。检查拒绝访问时同时记录实际可见反馈与操作前后状态。

在 `design/interaction-check.md` 为该 TC 记录输入、预期、实测，并链接 `[TC-01 运行](checks/TC-01.json)`。用同一套资料给 AI 接手：从 BL 内的控件状态和 AC 定位 TC，由 `acceptance-plan.json` 的 `pages` 找起始页与页面顺序，`checks/<TC>.steps` 指向实际控件与断言，原型 HTML 及引用的 CSS/JS 提供布局与事件处理。新增资料优先引用原件，PRD 的业务用语与页面一致。交接会核对已确认范围、各页断言、对象、步骤和运行所用文件的摘要。原型模拟结果仅供产品设计交接。

带 `reference` 的 TC 还须按[竞品 UI 对照](competitor-ui.md)复走相同任务并附对照证据。对截图、录屏使用已标出的画面或时间点，把人工实测的维度与仍待核的部分分别写清。

- 悬停钉点检查摘要，点击打开抽屉，核对主/替代/异常场景、业务规则、状态及 AC 表。验证悬浮开关可隐藏再显示钉点。
- 有“查看该状态”的页面，点击前后核对相应的实际反馈。用 hlbrowse 的 `expect-visible-text` 验证用户能看到的提示或空态文案；按钮置灰等行为按对应控件状态验证。使用 URL 回退的路径应重开正确的抽屉。
- 浏览器检查失败回到 6b 修稿；工具不可用时说明哪一页尚未验证及原因。已有模板自测结果只作为控件证据。

## 6b.6 设计评审

告知用户本版设计范围、完成的检查与待补项。按用户已选方式评审或登记免审，未选择时询问。评审时由 `designer` 核对规范与截图，`analyst` 对齐 PRD，`architect` 判断可行性。开发（`executor`）核对组件复用、实现量、状态转换和重复写入；测试（`test-engineer`）从用户入口复演成功、拒绝与恢复分支。要求分别评审时，两方对同版同一组 BL/AC 独立记录差异、证据及同条件复验结果。沿用微调区块、钉点与状态联动检查，登记实际参与者和待补证据。

请演示者从交付的 PRD 链接进入，按卡片完成任务，并复跑一个会改变结果的分支。若需要作者口头补充才能走通，把缺失的起点、文案或预期补回卡片并重试。作为前端 1:1 依据时，记录用户或指定负责人确认的版本、页面、状态、视口、证据与允许差异。免审或只跑过测试时如实记录，保留待确认项。确认后改动页面或交互时，复验受影响的 TC 并更新确认范围。

明确要求按已确认原型还原时，按[还原交接与复验](prototype-handoff.md)记录确认范围和对应 TC 基线，供后续开发与 QA 复用。

完整交接或明确要求机器复跑时，选一个会影响办理的交互承诺，在原型副本里只改错该行为，复跑对应检查点。例如将确认后的焦点移到筛选器，检查应指出原单详情的焦点不符。若仍通过，补上能区分两种结果的断言，用原件和改错副本各复跑一次。

驳回时回到 6b 修改并重评，三轮仍有分歧请用户决定。业务逻辑变化回到 4b，同步受影响的 PRD、设计和已产生的用例，按各自原评审选择处理。只交 PRD 与原型时，在 6b.6 返回 PRD、实际演示入口、实测结果与评审状态，至此结束。完整交接继续[步骤 8](SKILL.md#验收用例与交付)。仅维护历史双文件原型时查阅 [v18 设计规范归档](design-spec.md)。
