# 测试用例与候选验收

按当前任务选择起点。仅写用例时交清用例、依据和待测项。有候选要判断能否放行时执行正式验收。

| 当前任务 | 读取内容 |
|---|---|
| 写业务用例、评审覆盖范围 | 以下“测试用例编写”；涉及输入、列表、状态、权限等时选读[验收用例设计](test-design.md)。 |
| 测变更、做独立 UAT、接开发候选 | 以下“正式验收”。接收 JUnit、人工或竞品对照记录时读[候选验收报告](acceptance-reports.md)。 |
| 浏览器 E2E、响应式、重试、UI 还原 | [浏览器与端到端验收](browser-qa.md)。采用已确认原型或竞品时沿用产品约定的视口、动作与结果。 |
| 健康评分、比较历史基线 | [健康度与历史基线](health-baseline.md)，使用 `--health-only`。 |

## 测试用例编写

用例设计由 `test-engineer` 负责，执行由 `qa-tester` 负责，沿用[本库角色](../SKILL.md#agent-使用方式)。取得本期需求、已确认的原型或接口约定，逐 AC 写清前置条件、角色、操作、预期结果及可复跑的数据。覆盖适用的主路径、拒绝与边界、重试与恢复、跨角色或多入口的一致性。列出缺口、影响和所需决定。用户只要用例时到此交付。

每个可独立漏验的必测条件优先分不同 TC。一个 TC 约定多个共用参数、测试层或分片时，在计划登记[必测变体](acceptance-reports.md#必测变体)，实际报告逐项给出稳定标识。独立调用时与产品视角核对依据；已有同一修订的产品评审或免审记录时沿用。需独立签核时记录实际参与者、范围与结论。业务用例及开发补充的代码层用例沿用项目 `knowledge/tests/{module}.md`；代码层覆盖不足交开发补齐。

## 测试范围

有分支差异时，从 `git diff "$BASE...$CANDIDATE"` 找出受影响的页面、接口、命令和共享调用方。已有明确范围以该范围为准。Quick 做受影响入口冒烟，Standard 测关键路径、失败恢复与回归，Exhaustive 展开约定范围内的系统性边界、兼容性或无障碍审计。全量探索在授权范围内执行。本次属于正式验收时，完整运行确认计划的必测场景和变体。执行环境不可用时，保留最后成功步骤和缺测原因。

## 正式验收

1. 领取确认的 `acceptance-plan.json`、交接记录中的 `plan_sha256` 与 `spec_sha256`，以及开发交付的候选完整 SHA。独立 QA 只有经确认的计划时可省略 `--spec-sha256`。变更候选或修订范围后重新取得对应证据。
2. 用候选测试账号与真实入口重建前置条件。API 或 CLI 验请求、命令结果及副作用。UI 验到业务终态并记录所用视口。多页同单场景逐页核对对象和结果，计划含 `roles` 时保留同次办理的逐端观测。计划指定已确认原型或竞品时额外交对应基线的候选证据。[报告与对照格式](acceptance-reports.md)
3. 保存本次完整测试任务的最终退出状态、原始报告和实际被测提交。把 JUnit、人工记录或约定的对照结果列入同一份执行清单，从清单所在目录解析路径。在本次加载的 hltest 目录运行：

```sh
python3 "$HLTEST_DIR/qa-score.py" "$QA_DIR/run.json" --plan "$VERSION_DIR/acceptance-plan.json" \
  --plan-sha256 "$HANDOFF_PLAN_SHA256" --spec-sha256 "$HANDOFF_SPEC_SHA256" --candidate "$CANDIDATE"
```

默认输出 JSON，给开发看可加 `--summary`。逐 TC 报告通过、失败、跳过、缺测、证据失效及报告问题。全部必测通过返回 0；有阻碍返回 1；配置、摘要等输入错误返回 2。放行还须核对项目要求的各 CI 任务最终成功。没有证据时指出缺什么及该项可以怎样补测。

### 不稳定性策略

正式 Playwright 验收保留重试历史和 runner 的最终退出状态，首败后重试通过的必测项继续阻断，复跑修复后的稳定候选。[可运行的 CI 配置与判定](browser-qa.md#正式-ci-和重试)

### 生成和比较基线

需要健康评分或回归比较时，按[健康度与历史基线](health-baseline.md)固定范围、稳定检查 ID、实际运行证据和基线。核对候选是否满足需求时使用上面的正式验收。

## 交接段

只要报告时，将问题、严重度、预期、实测、候选版本、原始报告及复跑方式存入 `knowledge/qa/` 并交给用户。由开发或发布前 UAT 委派时交回 hldev / hlchain，部署后冒烟由 hldeploy 记录。获委派修复时按 [hlbug](../hlbug/SKILL.md) 查因，每轮复测受影响场景。引入新失败时撤回本轮修复并重新分析，单次会话达到 15 次仍未解决时交付阻碍与证据。可复用的缺陷模式按 [hlkb](../hlkb/SKILL.md) 记入知识库。路径沿用[项目约定](../hlpm/path-conventions.md)。
